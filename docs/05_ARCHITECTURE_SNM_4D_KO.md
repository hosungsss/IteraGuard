# 의심계 — 시스템 아키텍처, SNM 및 4D Ontology 운영 명세

문서 상태: 현행 설계 및 실행 범위 | 기준일: 2026-10-28 | 제품: IteraGuard / 의심계

## 1. 실행 구조와 신뢰 경계

```
합성 시나리오·수동 텍스트 [비신뢰]
  → 입력 유효성 검사 → 세션/버전 검사
  → 근거 주석 및 정확 구간 검증 [주석의 의미는 외부 검증 아님]
  → 주석 기반 4D Ontology(REQUESTS/REPORTS/WARNS_AGAINST/AMBIGUOUS)
  → 결정론적 안전 정책(4가지 비파괴적 사용자 안내)
  → 사용자 UI [SIMULATED 명시]
  → 확인 계획 기록(외부 사실 확인 완료가 아님)
  → 후속 입력 재평가 → 로컬 감사 이벤트 해시 체인
```

Zoro-1 검사용 Typed Decision 모듈은 분리되어 있다. 연결 실측 없이 현재 실행 경로에 `REAL_ZORO`가 존재한다고 주장하지 않는다. 모델 제안 출처(`MODEL_PROPOSED`)는 위험 행동 실행 권한이나 확정 의미 주석이 아니다.

## 2. 안전 정책의 불변조건

1. 송금·OTP 전달·원격제어 설치·민감정보 제공 등의 직접 요청이 **신뢰 가능한 시나리오 주석**에서 확인되면 `PAUSE_AND_VERIFY`. 이는 범죄 발생 확률이나 사기 확정을 뜻하지 않는다.
2. 제3자 인용·피해 신고·부정문·교육 문장은 직접 요청으로 승격하지 않는다.
3. 의미 충돌이 있는 중첩 근거, 모델만 제안한 주석, 근거 없는 수동 입력, 타임아웃 및 유효하지 않은 모델 출력은 `ASK_HUMAN` 또는 보수적 안내.
4. 모델 선택확률과 피해 발생 확률을 동일시하지 않는다. 보정 전후 수치·가짜 로짓·합성 시연 지연을 실측 연구결과로 표시하지 않는다.
5. 실제 금융·통신 시스템 제어, 앱 설치, SMS, 연락처 접근, 계좌 동결을 수행하지 않는다.
6. SHA-256 로컬 해시 체인은 동작 중 사후 기록 변조를 탐지할 수 있으나, 외부 공격자에게 대항하는 공증·영구 저장은 제공하지 않는다.

## 3. SNM — 대응 시나리오의 연결망

| 시나리오 패밀리 | 발화·상태의 핵심 구별 | 허용된 우선 대응 | 반례/실패 위험 |
|---|---|---|---|
| 정상 금융 안내 | 실제 행동 요청이 없다는 사전 검토 | `NO_STRONG_SIGNAL` | 범죄가 없다는 보증으로 오인 |
| 직접 송금 요청 | 화자가 수취자에게 직접 행동 요청 | `PAUSE_AND_VERIFY` | 합법 요청도 불필요하게 중지될 수 있음 |
| 인증번호 요구 | 비밀 인증정보 제공 요청 | `PAUSE_AND_VERIFY` | 'OTP 제공하지 말라'는 교육 발화와 혼동 |
| 원격 앱 설치 | 원격조작 가능 앱 설치 요청 | `PAUSE_AND_VERIFY` | 공식 기술지원이라는 주장만으로 신원 증명 불가 |
| 링크 클릭 요청 | 출처가 확실하지 않은 외부 주소 | `CAUTION` | 안전한 링크도 오탐 가능 |
| 제3자 신고·인용 | 타인의 지시를 인용하는 신고 | `CAUTION` 또는 문맥상 안전 안내 | 신고를 실시간 지시로 오인 |
| 부정문·교육 발화 | 하지 말아야 할 행동에 대한 설명 | `NO_STRONG_SIGNAL` | '위험 어휘' 중심 분류의 오탐 |
| 권위 주장·간접 화행 | 기관 이름·모호한 행동 압박 | `ASK_HUMAN` | 단정적 범죄 판정 또는 위험 누락 |
| 모델/통신 실패 | 추론 불가, 파싱 실패, 네트워크 타임아웃 | `ASK_HUMAN` | 과거 응답이 현재 상태로 남을 가능성 |
| 중복·역순 요청 | 세션 버전 충돌 | 거절 후 최신 상태 확인 | 사용자가 오래된 판단을 재사용 |

실제 사기 행위자는 적응적이므로 테스트 시나리오가 실제 공격 분포를 포괄한다고 주장할 수 없다.

## 4. 4D Ontology — 네 차원

- **구조:** `SpeakerClaim`, `Turn`, `EvidenceSpan`, `ActionKind`, `Directness`, `Provenance`, `PolicyDecision`, `VerificationIntent`, `AuditEvent`. 사실 관계가 아닌 '텍스트상 주장'과 '독립 확인'을 반드시 분리한다.
- **시간:** 시나리오 이벤트의 `turn`·`version`을 불변 증가시키고, 오래된 버전의 재평가를 거절한다. 이후 발화가 들어오면 과거 근거의 유효성은 다시 확인해야 한다.
- **관점:** 이용자(피해 예방), 정상 금융업무 담당자(오탐 비용), 평가자(데모 진실성), 기술팀(재현 가능성), 개인정보 주체(저장 최소화)의 비용을 함께 고려한다.
- **방향·검증:** 정책 결정 → 근거 인용구간 → 원문으로 역방향 추적; 신규 입력 → 근거 → 정책 → 기록으로 정방향 추적; 정상/위험 쌍의 반례로 검증한다.

## 5. 보안·프라이버시·운영 제약

현재 서버는 127.0.0.1 전용이며 HTTP Host 헤더를 확인한다. 이는 공용 서비스 인증이나 완전한 DNS 재바인딩 방어 인증이 아니다. 실제 민감정보 입력은 권장하지 않는다. 세션 이력에는 원문 전체를 저장하지 않지만 처리 중 메모리·브라우저에는 존재할 수 있다. 감사 체인은 무서명·메모리 기반이다.

## 6. 근거 분류

| 출처 유형 | 사용할 수 있는 주장 | 사용할 수 없는 주장 |

| 합성 Fixture | 주어진 사례에서 정책 일관성 | 실제 통화 탐지 정확도 |

| 독립 라벨 데이터 | 정의된 단위의 탐색적 성능 | 모집단 전체의 무조건적 성능 보장 |
| 독립 사용자 연구 | 특정 실험환경의 행동 변화 | 실제 경제적 피해 예방의 인과효과 확정 |

## 7. 실행 검증 기준

`python -m unittest discover -s tests -v` · `python scripts/evaluate_fixtures.py` · `python scripts/validate_skill.py` · `python -m prototype.server`로 반복 실행한다. 모든 결과에는 실행 환경·날짜·명령·모드·입력 표본 수·실제 결과를 기록한다. 샘플 수 14는 사전 작성 fixture 수이며 독립 검증셋 수가 아니다.


## 기업 지급 요청 검토 서브시스템

`GET /api/paylock/fixtures`는 공개 가능한 합성 거래처 샘플만 반환한다. `POST /api/paylock/evaluate`는 거래처·청구서 마스터와 입력을 대조한다. `POST /api/paylock/verify`는 reviewer가 기존 연락 경로로 확인했다고 보고하는 시뮬레이션 상태만 기록한다. 모두 localhost에서만 접근할 수 있다. 원문은 이력에서 제거하며, 전체 계좌는 메모리의 `Case`에도 저장하지 않는다. 외부 권한·송금 연계는 존재하지 않는다. 자세한 SNM/4D는 `docs/18_PAYLOCK_PILOT_AND_VALIDATION_KO.md`.

## 현행 비신뢰 출처의 지속 상태 오염 방지 및 지급 검토 재평가

기존 의심계의 위험 행동 경고와 PAYLOCK 지급 요청 검토에 공통되는 신뢰 경계는 **모델이 본 텍스트·외부 문서·도구 결과·복원된 기억이 실행 권한이 아니라는 것**이다. 출처의 표시 문자열과 실제 실행 하네스가 인증한 출처는 다르다. `preview_memory_prewrite`는 사용자·외부 문서·웹·도구 결과에서 메모리 후보를 받더라도 저장하지 않는 분리형 평가기로 동작한다. 외부 출처는 기본 격리, 확인된 사용자 선호도 실제 영속화하기 전에 별도 권한 계층이 필요하다.

PAYLOCK에서는 거래처·인보이스·계좌 비교가 서버의 가상 원장을 기준으로 수행되며, 메일 본문에 `SYSTEM:`이나 승인 무시 요구가 있더라도 새로운 권한이 생기지 않는다. 요청 재시도 시 추가 위험 신호는 이전의 내부검토 대기 상태를 보류로 격상시키며, 상태 버전과 감사 사건을 함께 갱신한다. 원문·계좌 전체·비밀번호·인증번호 저장은 기존 원칙대로 금지한다.

현행 검증기의 주요 반례는 정상 거래 유지, 외부 역할 가장, 사용자 출처의 미인증, 민감 정보 기억 후보, 모델 오류, 늦은 검토 신호, 기존 건 검토 완료 후 사건 변경, 내부 원장 오염, 인간 검토자 ID 가장이다. 메모리 API·실제 지급·고객 신원 인증·실제 모델/NPU 실행은 존재하지 않는다.

### 하네스의 실제 역할

Context는 사용자 요청과 외부 문서의 경계를 표현한다. Tools는 로컬 지급 검토·비파괴 안내를 제공한다. Constrain은 원문·모델 출력이 승인 정책을 우회하지 못하게 한다. Verify는 단위·통합·부정 테스트와 읽기·재검사로 뒷받침한다. Correct는 HOLD, 사람 확인, 새로운 위험 도착 시 버전 재평가로 제한한다. 이 절차는 Bojie Li의 『AI 에이전트를 깊이 이해하기』 제1·2·3·5·7·9장의 방법론에서 필요한 요소만 변용한 것이며, 책 속의 성능 수치가 제품 실측값인 것은 아니다.
