# 의심계 + PAYLOCK 현행 기술 감사

**현재 제품 범위:** 의심계 위험 발화 분석과 기업 지급 요청 검토(PAYLOCK)를 제공하는 로컬 합성 시연. **실제 검증 대상:** 로컬 코드·테스트·문서·압축 파일. 실 Zoro-1·은행·ERP·NPU·고객 효과는 검증되지 않았다.

## 소크라테스식 엘렌코스(모두 창작 문장)

> “위험한 계좌 변경을 찾아냈다는 사실이, 네가 모든 위험한 지급을 찾아냈다는 증거인가?”
>
> “기준정보가 거짓일 때도 규칙에 맞게 계산한 결과를 올바른 결과라 부를 수 있는가?”
>
> “AI가 새 기능을 추가할 때 정상 고객의 업무를 더 방해한다면 그것은 개선인가?”

**반증 대상 전제:** '의심계의 위험 인지 기능에 PAYLOCK을 결합하면 실제 지급사기 피해 예방에 곧바로 실용적이다.'

**반례:** 거래처의 진짜 이메일 계정이 탈취됐거나 은행/ERP의 등록 계좌가 사전에 공격으로 바뀌었다면, 프로그램이 현재 입력과 기존 값을 정확히 비교하더라도 실제 지급이 안전하다는 뜻은 아니다.

**답:** 비교는 *불일치를 발견하는 한 기능*일 뿐 계좌 소유권·발신인 인증·비용 효과의 증거가 아니다. 현재의 정확한 제품 가치는 실금융 방어가 아니라 **지급 요청 검토의 구체적인 절차와 책임 경계를 시연 가능하게 하는 것**이다. 프로덕션 도입에는 별도 데이터·인증·운영 통제가 필요하다.

## 현재 P1: 안전·운영·UX

- 정적 합성 원장 2거래처·3청구서는 실제 데이터 접근/업데이트·권한 동기화와 다르다.
- 원문·계좌번호는 HTTP 요청과 브라우저 입력에는 일시 존재한다. 감사 이력 미저장과 전송 시 보안 검증은 별개다.
- 단일 메모리 저장소의 데이터·검증 기록은 서버 재시작 시 사라지며 서명·외부 감사 보관이 아니다.
- 로그인/역할 인증·다중 테넌트 격리·외부 공개 서버 설정·요청 빈도 제한이 없다. localhost 전용 서비스로만 운영한다.
- 실제 브라우저 사용성/접근성·키보드 탐색/모바일 화면은 가능한 환경에서 별도 확인해야 한다.
- 영어·한국어 어휘 단서는 조작이 쉽고 인용·부정 범위를 완전하게 구분하지 않는다.
- 모델 점수 0.70은 제품 영역의 통계적 보정 임계값이 아니며, 동일 모델의 응답이 일관되더라도 계좌 진위를 입증하지 못한다.
- 사용자 최근 지시는 기술 개발 방향으로 해석하되, 공동 팀원의 서명된 제품 합의 및 IP·승인 권한은 별도 확인해야 한다.

## SNM·4D·NPU 판정

상세 SNM/4D는 `docs/18_PAYLOCK_PILOT_AND_VALIDATION_KO.md`를 따른다. 특히 시간상 늦은 검증 보고, 상충하는 duplicate request, 출처 주장과 인증 사실, 모델 응답과 정책 권한을 분리한다.

NPU: 하드웨어 제조사명이나 런타임 표시만으로 모델의 실제 typed head가 실행됨을 입증할 수 없다. 별도 GPU/CPU 실모델 경로조차 확인되지 않았다면 NPU 경로를 MVP 수용 기준으로 강제하지 말고 탐색 과제로 둔다.

## 검증의 올바른 해석

- 자동 단위·통합 결과는 코드/스키마/정책·회귀에 한정된다.
- 자가 작성 PAYLOCK 6개 사례를 모두 통과해도 독립 일반화 점수는 아니다.
- 코드에서 external payment action이 없다는 점은 실제 은행 동작이 성공했다는 뜻이 아니라 **해당 기능이 없다는 사실**이다.
- 제품 차별성의 핵심 질문은 `기존 계좌 대조만` 대비 `문장 해석 모델이 추가로 정상 업무를 방해하지 않으면서 어떤 잘못된 지급 위험을 더 찾아내는가`다. 이 질문의 실측 결론은 미정이다.

## 롤백 및 재수용 조건

PRD/정책 모순, 원문·계좌 정보의 감사 로그 노출, 실제 외부 동작, 모델 입력으로 지급 상태 강제, 기존 의심계 API 회귀 중 하나가 확인되면 릴리스 중단. 재수용 전에 코드 수정, 재현 실패 테스트, 전체 회귀, 패키지 매니페스트·CRC 재검증을 수행한다.
