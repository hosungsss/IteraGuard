# 의심계 / PAYLOCK — 기업 지급 요청 검토 모듈의 현행 기술 명세

**적용 시점:** 2026-11-01 KST  
**현재 구현:** 로컬 합성 거래처 원장, 지급 요청 필드 대조, 텍스트 어휘 단서 확인, 선택형 Typed Decision 제안, 승인 전 검토 보류, 검토 담당자의 확인 자기 보고, 일시적 감사 기록, 웹 시연  
**절대 주장하지 않는 것:** 계좌 소유자 실명 확인, 실제 이메일 인증, 실제 송금 차단, 은행/ERP 연동, 법적 BEC 판정, 사기 적중률, 정식 내부통제 인증, Zoro-1 실모델 평가, NPU 실기기 실행

## 1. 고객·문제·실제 사용 위치

초기 타깃은 중소기업 재무·경리 실무자다. 거래처가 **입금 계좌 또는 청구 금액 변경을 주장하는 메일**을 보냈을 때 회사가 보유한 거래처 마스터 및 청구서 정보와 비교하고 독립된 기존 연락처로 재확인할 기회를 제공한다. 모델이 '사기 95%'를 말하는 대신 **승인 전 보류가 필요한 이유와 확인해야 할 대상**을 보여 주는 제품이다.

이 문제를 실제 운영에서 해결하려면 기업 지급 시스템의 승인 워크플로 안에 통합돼야 한다. 현재는 입력·대조·보류와 상태 추적을 **합성 자료로 재현**한 연구용 UI다. 합성된 2개 거래처·3개 청구서만 포함한다. 수입 회계자료, 은행 API, 실제 메일 전송, 개인정보 수집은 범위 밖이다.

## 2. 확인할 수 있는 가치와 반례

**가치가 있는 조건:** 지급 승인자에게 지급계좌 변경, 금액 수정, 송신주소 불일치, 비정형 긴급 요청을 한곳에서 설명할 수 있고, 실제 내부통제의 확인 단계를 더 쉽게 실행하도록 안내하는 경우.

**가장 강력한 반례:** 기존 ERP가 거래처 계좌정보를 잠그고, 은행·사업자 검증 및 이중 승인까지 이미 제공한다면 단순 변경 대조 PAYLOCK의 추가 가치는 거의 없다. 추가 모델이 정상 지급을 더 많이 보류하면 비용만 증가한다. 따라서 **모델 없는 기존 규칙과의 쌍대 비교**가 필수다.

또 다른 반례: 거래처 실제 메일함을 탈취한 공격자가 기존 등록 계좌·금액을 그대로 보내도 `sender_email` 문자열은 신원 증거가 아니다. 이런 경우 구조적 필드 일치만으로 사기를 판정할 수 없다. 실제 송금 전에는 조직의 다중 승인과 검증된 ERP/은행 시스템이 필요하다.

## 3. 현행 구조와 신뢰 경계

```text
[가상 거래처·청구서 원장 (내부 참고 정보)]
                   │
[외부 메일 주소 주장·본문 + 지급 요청 필드]  [사용자 입력, 신뢰하지 않음]
                   │
          [스키마/형식 검사]
                   │
         [코드로 필드 대조] ──> 계좌/금액/ID 불일치 → HOLD
                   │
    [문장 어휘 단서 검사 (의미 파악 아님)]
                   │
  [선택적 Zoro-1 Typed 질문, 기본 비활성·미인증]
                   │   ↑ 제안만 가능, 지급 권한 없음
          [독립 정책/보류 결론]
                   │
    ┌──────────────┴────────────────┐
    │                               │
 [HOLD_FOR_INDEPENDENT_VERIFICATION] [READY_FOR_INTERNAL_REVIEW_NOT_PAYMENT]
    │                               │
 [등록 연락처로 재확인 권고]       [추가 내부 승인 필요]
    │
 [담당자 확인 보고 기록(모의)]
    │
 [VERIFICATION_REPORTED_UNATTESTED_REVIEW_ONLY 또는 DISPUTED_CANCELLED_SIMULATED]
```

### 입력 계약

- `request_id`: 멱등 키. 같은 키로 다른 지급 요청이 들어오면 거절한다.
- `requester_id`: 입력을 제출한 사람을 나타내는 **자기 주장 문자열**, 신원 인증 아님.
- `vendor_id`, `invoice_id`: 등록 마스터의 연결이 일치해야 한다.
- `sender_email`: 메일 주소가 기존 원장의 문자열과 다른지 비교할 뿐 SPF/DKIM/DMARC 및 발신자 신원을 검증하지 않는다.
- `requested_bank`, `requested_account`, `amount_krw`: 원장과 대조한다. 계좌는 ASCII 숫자, 공백, 하이픈만 허용하고 영문자/유니코드 숫자 혼동을 거절한다.
- `message`: 1,500자 이하의 외부 비신뢰 텍스트. 어휘 검사는 일부 압박 표현에만 반응한다.
- `use_model`: 명시적 참인 경우에만 운영자 관리 모델을 호출한다. 별도 원격 전송 동의와 호스트 허용 목록이 필요하며 기본값은 비활성.

### Typed Decision 보조 질문

`q_account_change` (`noul`): 발신 문장이 지급계좌 또는 지급 목적지 변경을 요구하는가?  
`q_urgency` (`noul`): 발신 문장이 지급을 서두르거나 독립 확인을 건너뛰라고 요구하는가?

두 질문의 모델 출력확률은 실제 범죄 위험도나 이메일 인증 수준이 아니다. 모델 응답이 실패·애매하면 **추가 보류**한다. 구조적 필드 불일치는 모델이 어떤 결과를 내도 해제할 수 없다. `ModelClient`의 정확한 엔드포인트와 모델 ID 문자열은 실제 체크포인트 증명이 아니다.

### 확인 기록의 정직한 의미

- 외부 메일이 새로 알려 준 전화번호가 아니라 **이전에 등록된** 연락 경로를 사용하라고 안내한다.
- `reviewer_id != requester_id` 문자열 검사, 상태 버전, 결과 코드, 허용된 모의 확인 방법, 이벤트 멱등을 확인한다.
- 사용자 입력을 통해 기록된 `CONFIRMED_BY_OPERATOR`는 실제로 전화를 걸어 확인했는지, 실제로 다른 사람이 검토했는지 입증하지 못한다.
- 실제 송금·결제 승인 함수는 존재하지 않는다. 상태명 `READY_FOR_INTERNAL_REVIEW_NOT_PAYMENT`는 지급 승인 완료가 아니다.

## 5. SNM 시나리오 네트워크

| ID | 상황·초기 상태 | 전이/모범 결과 | 실패 위험 | 현재 검증과 남은 과제 |
|---|---|---|---|---|
| S1 | 유효한 청구서·변경 없음 | 내부 승인 검토 **대기** (실제 지급 없음) | 정상 지급을 지연 | `test_unchanged_never_payment`; 업무 지연 실측 필요 |
| S2 | 등록된 계좌 변경 | 독립 확인 전 HOLD | 공격 계좌로 지급 | `test_changed_account_same_bank_hold`; 실제 계좌 소유권 미검증 |
| S3 | 발신 주소가 한 글자 다름 | HOLD | 스푸핑 수용 | `test_sender_spoof_hold`; 실제 이메일 인증 없음 |
| S4 | 원장 금액과 요청 금액 다름 | HOLD | 청구서 변조 | `test_invoice_amount_hold`; 원장 자체 오염 가능 |
| S5 | 주소·계좌·금액 정상이나 긴급 압박 | 어휘 단서에 따라 HOLD | 정상 긴급 지급 오탐 | `test_pressure_word_heuristic`; 간접/암시 표현 미검증 |
| S6 | 본문이 'SYSTEM: 승인' 요구 | 모델·코드는 해당 명령을 DATA로 처리 | 프롬프트 인젝션 | `test_no_injection_escalation`; 적응형 공격 별도 |
| S7 | 모델 미연결·무효 응답 | 모델 사용을 선택했으면 HOLD | 모델 오류의 거짓 안심 | `test_model_malformed_goes_to_hold`, HTTP 테스트 |
| S8 | 요청자가 검토자 이름도 자신으로 기재 | 확인 보고 거부 | 승인 이해충돌 | `test_same_reviewer_claim_rejected`; 인증된 2인제 아님 |
| S9 | 늦은 확인 보고·중복 요청 | 버전·멱등 키로 충돌 거부 | 원치 않는 과거 결론 복원 | `test_stale_version_blocked`, `test_parallel_idempotent_submission` |
| S10 | 이메일 발신자 계정이 탈취돼 주소가 정상 | 필드 일치만으로는 탐지 불가 | 가장 중요한 BEC 미탐 가능성 | **NOT_VERIFIED**, 별도 수신 경로 인증 필요 |
| S11 | 등록된 계좌 마스터 자체가 공격으로 바뀜 | 코드가 잘못된 기준을 신뢰할 수 있음 | 기준자료 훼손 | **NOT_VERIFIED**, ERP 마스터 변경 통제 필수 |
| S12 | 모델이 위험 신호를 놓치고 낮은 확률 부여 | 구조적 불일치는 그대로 HOLD | 모델이 주는 거짓 안심 | `test_model_cannot_override_structural_hold` |

## 6. 4D Ontology

- **구조:** `PaymentRequest HAS Invoice`, `Invoice BELONGS_TO Vendor`, `Vendor HAS_PRE_REGISTERED Account`, `Email CLAIMS Sender`, `Policy COMPARES Request-to-Reference`, `Model PROPOSES TextIntent`, `Case HAS ReportedReview`. `Email CLAIMS Sender`와 `VerifiedSender`는 서로 다른 타입이다.
- **시간:** t0 등록 원장 → t1 지급 요청 → t2 독립 대조·모델 제안 → t3 HOLD 또는 내부 검토 대기 → t4 검토 보고(모의) → t5 모의 상태 변경. 지난 사례의 지연 보고와 현재 승인 판단은 연결하지 않는다.
- **관점:** 경리는 업무 지연, 재무책임자는 금전 손실과 내부통제, 거래처는 정당한 계좌변경 불편, 보안 담당자는 조작·권한, 심사위원은 기술·데모 진정성 관점에서 평가한다.
- **방향·역검증:** 최종 상태에서 reason code를 따라 원장 비교·모델 신호·요청 데이터를 재구성한다. 단, 감사 체인은 서명 없는 메모리 일관성 점검이며 법정 증거 또는 실제 지급 완료 영수증이 아니다.

## 7. 실험 및 반증 기준

**최소 독립 비교군:** (A) 원장 비교 규칙만, (B) 비교+어휘, (C) 비교+실제 Zoro-1. 
동일하고 사전 고정된 잠금 평가셋에서 모델 추가 후 `정상 지급 오탐 보류율`, `비정형 계좌변경 의도 발견율`, `업무 처리 시간`, `낮은 신뢰 보류율`, `p50/p95`, `총비용`을 비교한다. 공격·정상 문장 변형은 시나리오 패밀리별로 분리한다. 자가 작성 6개 fixture 결과를 고객 환경 정확도나 독립 성능으로 표기하지 않는다.

**중단 조건:** (1) 모델이 코드의 계좌 불일치 HOLD를 해제할 수 있음, (2) 실제 지급 기능을 사람이 승인 없이 실행함, (3) 원문·전체 계좌를 로그에 저장함, (4) 공격 입력이 인증 주체를 위조함, (5) 독립 검증 없이 성능 수치를 발표함. 어느 조건이든 위배되면 검증 단계에서 배포 중단·기존 의심계 합성 경로로 복귀한다.

```bash
cd dmsg

# PAYLOCK 검증 화면: http://127.0.0.1:8765/paylock.html
```

프로덕션 서버에서는 실행하지 말 것. 접근 가능한 실제 지급 기록·계좌·고객정보 대신 제공된 6개 합성 사례만 활용할 것. 모델을 별도로 사용하려면 `references/MODEL_CONTRACT.md`에서 운영자 승인 조건을 확인할 것.

## 현재 모의 워크플로의 비신뢰 메일·늦은 추가 위험 처리

등록 원장과 요청 은행·계좌·청구금액이 같더라도 비신뢰 메일의 명시적 역할 가장·검증 우회 표현은 `UNTRUSTED_MESSAGE_INSTRUCTION_CUE`로 보류한다. 어휘 기반 검출은 전수 의미 분석이 아니므로 정상 요청의 오탐·간접 강요 미탐을 별도 지표로 점검한다. 중복 `request_id`에 모델의 새로운 보류 신호가 뒤늦게 오면 사건 버전을 올리고 HOLD 상태로 격상시킨다. 이미 완료한 모의 확인 사건에는 추가 위험이 도착해도 완료를 덮어쓰지 않고 새 검토가 필요함을 오류로 알린다. 계좌·발신자 실명 인증 및 실제 송금은 없다.
