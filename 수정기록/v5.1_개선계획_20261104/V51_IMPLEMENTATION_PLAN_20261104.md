# 의심계 v5.1 개선 계획

작성일: 2026-11-04 KST. 상태: **계획 초안 / 구현·신규 실험 미착수**. 기준은 사용자 지정 모음의 `[v5.0] IteraGuard_DoubtMeter`다. 현재 최신 버전은 v5.0이며, 이 문서를 작성하는 것만으로 v5.1 릴리스나 실험 사전등록이 완료되지는 않는다.

## 목표와 우선순위

v5.1의 주목표는 **정상 문장에 대한 불필요한 보류를 줄이고, 실제 중단해야 할 요청을 더 정확히 중단하도록 만드는 것**이다. 근거 표시의 의미 품질도 함께 고친다. 이미 검증한 공통 계약·세션·종료/재개·배포 기반은 회귀 검사로 지킨다.

버전 번호 변경, 테스트 통과, 모델 API 연결 성공으로 판단 성능 개선을 대신하지 않는다. 개선 후보가 채택 기준을 통과하지 못하면 v5.0을 유지하고 v5.1은 실험 후보 상태로 남긴다.

## 근거: 현재의 실패와 먼저 확인할 가설

아래 숫자는 `internal/evidence/v50/question_ablation/comparison.json`의 원본 조건에서 읽었다. 모두 이미 본 합성 개발 데이터이며 실제 서비스 정확도나 독립 평가 결과가 아니다.

| 항목 | v5 현재 관측 | 계획에 주는 의미 |
|---|---|---|
| 새 AI 25개 기대 안내 일치 | legacy 14/25, DRA 17/25 | 단일 일치율로 채택하지 않음 |
| 정상 12개의 보류 | legacy 11/12; 이 중 허용 안내 밖 ASK 8개, 허용된 ASK 3개 | 허용된 보류와 불필요한 보류를 분리해 평가 |
| 필수중단 8개의 중단 누락 | legacy 3/8 | ASK_HUMAN도 필수중단 실패로 별도 집계 |
| 이전 V2 48개의 필수중단 누락 | legacy 7/9 | 새 25개만 좋아지는 변경을 채택하지 않음 |
| evidence_only 후보 | legacy 전체 개발셋에서 기대 일치 이득 3, 관측된 기대 일치 손실 0 | 작은 변경을 새 프로토콜로 재검증할 근거 |
| 기존 evidence_only HOLD | DRA에서 V02 경고문 ASK→CAUTION으로 허용 안내 밖 출력 | 옛 HOLD를 그대로 보존하고 배포 정책별 새 검증을 설계 |
| action/speech 변경 | 다른 head 확률도 94~97개에서 변동 | 질문 하나 수정도 전체 분포·정책 결과를 다시 비교 |

정상 문장이라고 ASK가 모두 오답은 아니다. 새 AI 25개에서 불필요 ASK 8개는 V50-AI-01/02/03/06/07/08/11/12이며, 04/05/09의 ASK는 현재 주석에서 허용된다. 정상 10은 ASK가 아니었다. 이 주석 자체도 AI 제안이므로 사람 검토 대상이다.

현재 핵심 가설은 다섯 가지다. 원인별 사례를 확인하고 실제 기여를 분리한 뒤 고친다.

1. **요청 없음과 분류표 밖 요청의 혼동**: `none`은 모델 문구상 요청 없음이지만, 방문/준비물 요청처럼 민감행동 목록 밖의 요청도 있다. `none+direct_request`를 충돌로 보류하는 현재 규칙과 의미가 어긋날 수 있다. 이 충돌을 무조건 해제하면 간접 위협도 놓칠 수 있다.
2. **근거 충분성 문항의 범위**: 완전한 무행동 안내문에도 행동/압박 근거를 요구해 보류할 수 있다. 분류에 충분한 정보와 위험을 뒷받침하는 근거를 구분할 필요가 있다.
3. **부정·인용·새 요구가 한 문장에 섞임**: 경고/사례 설명 뒤의 실제 OTP 요구 등에서 문장 전체 화행이 현재 요구를 가릴 수 있다.
4. **복수 행동과 정상 송금**: 링크+OTP+개인정보의 복수 행동을 단일 대표 라벨이 놓칠 수 있다. 송금 라벨 자체로는 일상 송금과 강요를 구분할 수 없다.
5. **근거 표시의 의미 부족**: `주세요` 같은 어미가 원문에 존재한다는 사실만으로 행동·대상·압박을 설명할 수 없다. offset 정확성과 설명 품질은 별개다.

### 1단계: 실패 원인과 평가부터 고정

기존 98개(빈 문장 1개 포함)를 모두 개발/회귀셋으로 취급한다. 실제 추론 대상은 97개이며, 빈 문장은 추론 없이 처리한다. 모델 출력 → 정규화 → 충돌 guard → 정책 → 로컬 후처리 → 세션 결합 중 어디서 안내가 바뀌었는지 케이스별로 기록한다.

원본 라벨은 덮어쓰지 않는다. 예를 들어 AI-JM-02의 방문 요청을 INFORMATION으로 적은 문제는 별도 주석 수정 제안과 버전으로 기록한다. 모델 결과를 본 뒤 정답을 바꿔 점수를 올리지 않는다. 복수 행동·맥락 부족·허용 안내 집합·필수중단 여부를 분리한다.

`docs/V50_TRACEABILITY.json`의 RELEASE-V50-G02는 제목이 독립 평가인데 implementation_status는 원본 72개 재현을 근거로 VERIFIED_LOCAL이다. v5.1 추적표에서는 **개발 재현**과 **사람 독립 평가**를 서로 다른 ID로 나누고 실제 상태를 적는다. 기존 문서는 역사 원문으로 유지한다.

### 2단계: 가장 작은 개선 후보를 먼저 검증

원본 7문항, 선택지 순서, T=1.52, 모델 가중치, legacy 정책/0.70을 고정하고 evidence 문항만 바꾼 후보를 먼저 비교한다. 이는 과거 HOLD 후보를 소급 채택하는 작업이 아니다. 신규 데이터와 제품 기본 정책에 대한 채택 기준을 먼저 동결하는 새 실험이다.

DRA의 새 질문 호환성은 별도다. legacy 후보의 결과를 검증 없이 DRA로 보내지 않는다. DRA를 보존한다면 검증된 v5 질문·정책 묶음으로 별도 비교하거나, v5.1 후보와의 조합을 미지원으로 표시한다. trace와 질문 계약 지문으로 실제 사용 묶음을 구분한다. 현재 앱은 응답을 받은 뒤 legacy/DRA를 고르는 흐름이 있으므로, v5.1에서는 **모델 요청 전에 질문 profile·정책 ID·질문 해시를 고정**하고 응답/trace에 결합해야 한다. 요청 중 선택을 바꾸면 이전 응답을 새 정책/profile에 그대로 적용하지 않는다. 기존 질문/전송 어댑터를 제한적으로 확장하며 서버 전체를 다시 만들지 않는다.

이 단계가 과보류만 줄이고 필수중단 누락을 고치지 못하면, 이를 v5.1 최종 개선 완료로 처리하지 않는다. 기존 action_only/speech_only의 단순 조합도 자동으로 채택하지 않는다.

### 3단계: 요청 의미와 정책을 함께 개선

작은 수정 이후 남는 원인에 맞춰 최대 두 개의 구조 후보를 먼저 설계한다. 추가 질문/라벨을 실제 Typed 계약이 지원하는지 확인하고, 원본 계약과 다른 버전으로 정의한다. 현재 q_evidence는 optional이며 알 수 없는 새 키는 거부된다. 각 필드의 필수/선택 여부와 누락·오형식 fallback을 정의하고, 위험 해제에 필요한 새 필드가 없을 때 정상 판단으로 통과시키지 않는다.

- **후보 B1 — 요청 존재와 행동 종류 분리**: 요청 유무 yes/no/unclear와 민감행동 종류를 구분하고, 목록 밖 행동을 `other_action`처럼 별도 표현하는 안을 비교한다. `other_action`은 무해함이나 안전을 뜻하지 않는다. 불명확한 요구와 간접 압박을 정상으로 자동 처리하지 않는다.
- **후보 B2 — 현재 요구·복수 민감행동 보강**: 경고/인용 속 언급과 지금 청자에게 하는 요청의 관계를 확인하고, OTP/원격접속/개인정보 등 중단 대상 행동이 대표 라벨에 가려지는지 비교한다. 필요하면 지원되는 추가 Typed 문항으로 확인한다. 모든 문장을 추가 모델 호출로 보내는 구조는 기본안에 넣지 않는다.

정상 송금은 별도 경계 유형으로 다룬다. 송금 표현이 있다고 전부 중단하지 않고, 평범한 문구라는 이유로 인증된 거래로 판정하지도 않는다. 현재 문장에 없는 발신자 신원·거래 맥락을 지어내지 않는다. 허용 안내와 필요한 확인 작업을 제품 rubric에 명시한다.

질문 변경과 정책 변경을 한 번에 섞지 않는다. 먼저 원본 raw에 새 guard/정책을 적용하는 추론 0회 재생으로 영향을 분리한다. 이는 기존 필드만으로 계산 가능한 변경에 한한다. B1/B2의 새 head·라벨에 의존하는 정책은 v5 raw로 재생할 수 없으므로, 실제 후보 응답을 수집해야 한다. 새 필드를 임의 추정하거나 정상 기본값으로 채우지 않는다. 그다음 질문 후보의 새 raw와 결합해 최종 계약 전체를 검사한다. 기존 0.70/DRA 비용표를 내리는 방식은 첫 해결책으로 삼지 않으며, 조정한다면 별도 사전등록 실험으로 다룬다.

Python과 JS는 같은 schema·질문 순서·정책 ID·오류 처리를 사용한다. 기존 ModelClient의 question_payload 주입점을 재사용하고, 후보 profile은 한 곳에 정의해 Python/JS로 생성·검증한다. 현재 Python은 vendor/dmsg, JS export는 dmsg를 읽는 이중 경로가 있어 두 경로의 질문/정책 동기화를 명시적으로 검사한다. v5 raw를 v5.1 schema로 조용히 해석하지 않고 구버전·신버전 입력 계약을 명시적으로 나눈다. 기기 내 NLP는 별도 모델이므로 새 Typed 질문 성능을 NLP 성능으로 설명하지 않는다.

### 4단계: 근거와 설명 품질

행동 동사·대상·요구 내용·압박 단서를 가능한 경우 같은 절의 원문 구간에 연결한다. 인용/경고와 현재 요구를 구분해서 표시하고, 어미만으로 위험 근거가 있는 듯 표시하지 않는다. 의미 있는 구간을 찾지 못하면 근거를 추정해서 채우지 않고 `근거 구간 확인 불가`로 표시한다.

문자 위치 검사와 의미 검사를 나눈다. Python/JS의 Unicode 위치, 줄바꿈, 겹치는 구간, 한글/이모지, 복수 절에 대한 회귀와 사람이 보는 근거 의미 적절성을 각각 평가한다. 의미 적절성뿐 아니라 근거 미표시율과, 의미 있는 원문 근거가 있는 사례의 표시 coverage도 공개한다. 모든 근거를 숨겨 오류 0을 만든 결과는 품질 개선으로 채택하지 않는다. 표시 개선이 판단 정책까지 바꾸면 별도 정책 변경으로 다시 검증한다.

### 5단계: 통합·상태관리 보호

브라우저에서 정상 안내, 일상 요청, 명확한 OTP/원격 요구, 경고+새 요구, 모호한 협박, 링크+OTP 복합 요청을 실제 Typed 경로로 검사한다. 모델 미연결·응답 스키마 오류·계약 불일치·중복 요청·오래된 응답·긴 한글 입력도 검사한다.

아레나의 prior_pause 보존, 자기보고가 위험 해제를 뜻하지 않는 경계, CLOSED_UNRESOLVED 종료/재개, 작업 중복 억제는 유지해야 한다. 현재 정상 문장과 과거 위험 때문에 남은 세션 보류를 화면에서 각각 설명한다. PC 단문 앱에 아레나의 세션 이력을 암묵적으로 섞지 않는다.

기존 PAYLOCK·LinkGuard/APK·도메인·메모리/harness는 영향 범위에 맞춰 회귀 검사한다. 이미 완료된 v5 세션/계약 기능을 신규 개발 항목으로 재계산하지 않는다.

## 데이터와 실험 설계

1. **기존 98개**: 개발/회귀. 기존 입력·라벨·raw·실패 로그 불변 보존.
2. **새 AI 대조 사례 60개 초안**: 20개 family×3개 의미 대조를 권장한다. 요청/부정/인용, 정상 송금/압박 송금, 목록 밖 요청, 간접 위협, 복수 행동, 맥락 부족을 포함한다. family 단위로 개발 36개와 잠금 검증 24개를 나누고 유사 문장을 양쪽에 나누지 않는다. 기존 사례의 단순 바꿔쓰기는 새 독립 family로 세지 않는다.
3. **사람 독립 평가 40~60개**: 진명·호성이 서로 보지 않고 각 20~30개 작성하는 기존 원칙을 유지한다. 모델 결과와 후보 선택을 보지 않은 주석, 이견 기록/해결, 최종 잠금을 적용한다. AI 60개는 이 평가를 대체하지 않는다.

사례 작성·주석 검토와 분할이 끝난 후 후보·질문·정책·모델 해시·실행 순서·통과 기준을 프로토콜로 등록한다. 현재 문서는 프로토콜 초안이지 데이터가 동결됐다는 영수증이 아니다. 3단계에서 잠금 결과를 본 뒤 4~5단계에서 판단 경로를 수정하면, 같은 잠금셋을 최종 확인에 재사용하지 않는다. 잠금셋 결과를 보고 수정하면 그 세트는 개발셋으로 전환하고 새 잠금셋을 확보한다. 사람 최종 평가는 근거 표시와 후처리·세션 연결을 포함한 전체 판단 경로를 동결한 뒤 시행한다.

질문 변경 후보는 새 추론이 필요하다. 정책/표시만 바뀌면 기존 raw 재생부터 수행한다. 요청 수는 후보 수×비어 있지 않은 사례 수로 사전에 산정하고 실제 호출·오류·재시도·재생 횟수를 따로 남긴다. 먼저 작은 원인별 시험을 하고 통과한 후보만 전체 비교한다.

## 채택 기준

제품 기본 경로에 대해 다음을 후보 결과를 보기 전에 확정한다. DRA 비교 경로의 기준/지원 조합은 별도로 명시한다. 기존 v5 프로토콜을 고쳐 과거 후보를 통과시키지 않는다.

| 게이트 | 제안 기준 |
|---|---|
| 위험한 정상 처리 | 검증셋의 위험/맥락 부족 사례를 NO_STRONG_SIGNAL로 새로 내보내는 회귀 0 |
| 필수중단 | 기존에 맞힌 필수중단 사례의 새 누락 0. 전체 기존 회귀셋에서 누락을 줄이고, 신규 잠금셋에서도 기준선 대비 악화 없음. 기준선 누락이 있는 신규셋에서는 개선 확인 |
| 정상 부담 | 정상 문장의 불필요한 ASK_HUMAN 감소. 신규 잠금셋에서도 같은 방향 확인. 정상 PAUSE 및 경고/인용 과개입 증가 없음 |
| 기대 안내 | 기존에 허용된 안내를 벗어나는 새 손실 0. 모호한 주석은 결과 확인 전에 확정하거나 별도 집계 |
| 근거 의미 | 어미 단독을 위험 근거로 제시하는 오류 0. 표시한 구간의 원문 위치 일치 100%, 미표시율/표시 coverage와 의미 적절성을 별도 공개. 표시 구간이 0이면 위치 품질은 N/A이며 합격 근거로 쓰지 않음 |
| 계약/상태 | Python/JS 출력·규칙·지문 일치, 오류 시 숨은 대체판단 없음, 세션 과거 위험·종료/재개 보호 |
| 재현/지연 | 고정 런타임 재현 확인. 차가운 시작/따뜻한 요청을 구분하고 p50/p95·요청 수·입력 길이 변화 공개. 추가 호출 도입은 별도 채택 판단 |

이미 본 새 AI 25개에서의 **개발 목표안**은 허용 안내 밖 정상 ASK 8/12를 3/12 이하로, 필수중단 누락 3/8을 1/8 이하로 낮추는 것이다. 허용된 정상 ASK는 별도 집계하며 무조건 제거하지 않는다. 목표 달성을 보장하지 않으며, 이 숫자를 맞추는 것만으로 채택하지 않는다. 전체 회귀·새 잠금셋·독립 평가 결과가 우선이다. 각 비율은 분자/분모와 사례 ID를 공개하고 작은 표본의 변동성·불확실성을 함께 설명한다.

NO_STRONG_SIGNAL/CAUTION/PAUSE_AND_VERIFY/ASK_HUMAN을 단순한 강약 순서로 보지 않는다. ASK가 줄었다고 성공이 아니며 필수중단이 ASK로 바뀌면 실패다. 현재 턴 안내와 과거 위험이 결합된 세션 안내의 분모도 각각 집계한다. 항상 ASK 기준선과도 비교해 불필요한 보류로 점수를 얻는 평가를 막는다.

## 릴리스 범위와 사용자에게 필요한 일

개발·디버깅·AI 대조 사례는 자동으로 진행할 수 있다. 사람 독립 평가 문장과 구체 팀 합의는 실제 작성/합의 기록이 필요하다. 준비되지 않아도 개발 실험을 진행하되 해당 게이트는 NOT_RUN으로 남긴다. 개발 검증까지만 끝나면 `v5.1 RC/개발 후보`, 사람 독립 평가까지 통과한 범위만 최종 결과로 설명한다.

Android 실기기 검증은 실제 설치/입력/오프라인/모델 모드를 확인했을 때만 완료다. iOS·새 OS·실제 기관 확인을 v5.1 전체 성공의 일부로 묶지 않는다. 검증한 웹/Linux 범위와 미검증 기기 범위를 구분한다. L2 본문/G7/기관 질문/L1은 승인 전 현행 유지다. 행사 GPU/API·외부 API 허용·제출 조건도 공식 확인 범위에 맞춰 별도 기록한다.

실행 코드는 v5를 복제한 별도 v5.1 작업본에서 수정한다. v5.1 소스·PRD·시스템 지침·질문/정책 manifest·원장·전후 비교 보고·실험 프로토콜/raw·브라우저 증거·검증된 앱 배포물을 만든다. FULL은 소스 밖에 만들고 독립 추출본에서 다시 검증한다. 합격한 경우에만 LATEST_VERSION.json을 v5.1로 전환한다.
