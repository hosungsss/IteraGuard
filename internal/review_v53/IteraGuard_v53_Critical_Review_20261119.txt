IteraGuard / 의심계 v5.3 — 해커톤 경쟁력·구현·증거 비판 검토
검토일: 2026-11-19 KST
대상: 지정된 Google Drive 프로젝트의 최신 v5.3 폴더
검토 성격: 읽기 전용 검토, 저장 자료 검산, 통제 응답을 이용한 로컬 재현

1. 판단

현재 방향을 유지하되, 제출의 중심을 “Zoro가 현재 요청을 판단하고, 미해결 위험과 확인업무를 관리하는 에이전트”로 명확히 하는 것이 적절하다. Zoro가 단순 설명문만 만드는 구조는 아니다. 질문·응답 계약과 상태 관리에는 실제 구현과 검증 자산이 있다.

가장 큰 병목은 모델 추가나 문서 확대가 아니다. 현재 기본 실행 화면, 모델의 판단이 최종 행동에 반영되는 경로, 새로운 불확실성에 대한 확인업무 갱신, 발표 장비의 실제 실행을 하나로 연결하는 것이다.

이번에 재현한 워크플로 결함은 “이전 확인업무 완료 보고 + 다른 새 메시지의 ASK_HUMAN” 뒤 새 업무가 생기지 않는 경로다. 별도로, 최신 공식 /v1/decide 서버로 바꾸면 기존 /v1/systemone 전용 클라이언트가 거부한다는 조건부 호환성 위험을 확인했다.

우승 가능성의 숫자나 공식 배점을 임의 평가하지 않았다. 아래 P0/P1은 이번 제출 준비를 위한 내부 우선순위다.

2. 무엇을 실제로 확인했는가

직접 확인:
- Drive 루트 및 최신 v5.3의 핵심 문서·코드·질문 계약·평가 자료.
- 활성 v5.1 실행 manifest의 소스·프로필 지문 일치.
- 활성 11문항 프로필: v51-specific-candidate.
- Python 핵심 execution 테스트 13/13 PASS.
- Python profile 테스트 12/12 PASS.
- Node 최소 DOM에서 production UI 스크립트 테스트 16/16 PASS.
- 통제한 Typed 응답으로 실제 정책·후처리·SQLite를 실행한 새 ASK 업무 누락 재현.
- /v1/decide endpoint 설정의 네트워크 이전 거부 재현.
- AI24 원시 응답 48개, 정책 결과 48개, 라벨 24개를 대조한 지표·사례 ID 검산.
- 최신 공식 대회 홈페이지·Zoro 모델 카드·Trida Decision 문서와 비교 제품 공식 설명.

이번에 실행하지 않은 것:
- 새로운 Zoro 추론: 0회.
- 사용자 발표 장비의 실모델 완주·콜드 스타트·동시 부하.
- 실제 브라우저 시각 렌더링·Android/iOS 실기기.
- 실제 통화 수집·기관 확인·은행 제어·지급.
- 사람의 독립 라벨링이나 실제 피해예방 효과 평가.
- 모든 과거 버전의 전수 검토, GitHub 제출·접수 상태 확인.

따라서 “현재 연결 모델까지 라이브 검증 완료” 또는 “전체 제품 검증 완료”라고 표현하지 않는다. 반대로 과거 실제 실행 기록이 존재하는데 “한 번도 Zoro를 쓰지 않았다”고 평가하지도 않는다.

3. 현재 상태와 버전 혼선

v5.1은 실제 로컬 Zoro 실행을 포함한 판단 개선의 근거가 저장된 개발 후보다. 전체 장부 557회는 544+13 및 제공자 카운터 1349−792와 산술적으로 일치한다. 이번 검토가 557회 전부의 원시 결과를 다시 계산한 것은 아니다.

v5.2의 5특징 로지스틱 미들웨어는 탐색용이며 production_authority=False, may_override_v51_policy=False이다. 활성 v5.1 판단 경로에 들어 있지 않다.

v5.3은 기존 판단 계약을 유지하고 선택·정책·UI 설명과 배포 도구를 손본 후보다. v5.3의 LIVE_MODEL_CALLS=0은 그 변경 작업에서 새로운 모델 호출을 하지 않았다는 뜻이다.

루트 README.md와 LATEST_VERSION.json은 아직 v5.1을 가리킨다. v5.3 내부도 패키지 버전과 엔진·앱 내부 버전 5.1을 구분한다. 이 구분 자체는 가능하지만, 심사자에게 제시할 최종 진입점은 하나여야 한다.

특히 docs/07_DEMO_AND_PITCH_KO.md에는 현재 합성 정책 루프에 Zoro가 연결되지 않았다는 답변과 모든 UI에 FIXTURE/SIMULATED를 유지한다는 오래된 설명이 남아 있다. 이는 v5.1 이후 실제 Typed 경로와 충돌한다. 역사 문서를 삭제할 필요는 없고, 현재 발표용 문서와 역사 자료를 명시적으로 구분하면 된다.

근거: README.md, CURRENT_PROJECT_STATE.md, PRD_v51.md, V51_IMPLEMENTATION_REPORT.md, V53_VALIDATION_REPORT.md, 07_DEMO_AND_PITCH_KO.md.

4. 먼저 수정할 문제

F01 / P0 / 시연의 기본 경로가 핵심 모델·세션 기능과 갈라져 있다

관측:
apps/web/index.html에서 온디바이스 NLP는 기본 선택, 실제 Zoro는 기본 미선택이다. apps/web/app.js의 run()도 이를 따른다. 예시 시나리오 입력은 fixture 분기로 먼저 들어간다. 모델 설정이 감지되었다는 상태와 실제 Zoro 선택은 별개다.

단문 화면은 현재 문장만 분석하고 세션의 과거 위험을 결합하지 않는다고 명시한다. 과거 위험·확인업무를 관리하는 기능은 별도 Arena 화면에 있다.

영향:
단문 앱을 기본 설정 그대로 보여주면 “Zoro 기반 에이전트”의 핵심 기능을 시연하지 않을 수 있다. 디자인이 더 풍부한 화면을 선택하더라도 핵심 차별점인 세션 추적이 보이지 않을 수 있다. 이는 규정 위반이 확정됐다는 말이 아니라 발표 경로 선택의 위험이다.

최소 수정:
해커톤 전용 진입점을 하나 정한다. 우선 Arena의 실제 Zoro 경로를 본편으로 삼고 단문·온디바이스·PAYLOCK·LinkGuard는 보조 기능으로 둔다. 입력 출처(작성된 합성 대본)와 추론 출처(실제 Zoro/저장 응답 재생/fixture)를 별도 표시한다.

검증:
새 세션 → 입력 → 실제 요청 → 최종 안내 → 확인업무 → 상태 재조회가 같은 화면에서 이어지는지 확인한다. 합성 대본을 썼다는 이유로 실제 추론까지 fixture로 표기하거나, fixture 응답을 라이브로 표기하지 않는다.

F02 / P0 / 다른 새 메시지가 ASK이면 후속 확인업무가 사라질 수 있다

재현 순서:
1) 첫 문장 “그 자료를 안내받은 곳으로 보내 주세요.”에 통제된 불확실 Typed 응답을 주입한다.
2) 실제 현행 evaluator 결과 ASK_HUMAN 및 OPEN 확인업무가 생성된다.
3) 그 업무에 USER_REPORTS_CONFIRMED를 기록하면서 다른 문장 “다른 문서도 새로 받은 번호로 보내 주세요.”를 평가한다.
4) 새 현재 턴도 ASK_HUMAN이지만 next_task가 없고 이전 REPORTED_COMPLETE 업무만 related_task로 반환된다.
5) 열린 업무 수는 0이다.

원인:
arena/store.py의 new_risk_input 조건이 PAUSE_AND_VERIFY와 CAUTION만 포함하고 새로운 현재 턴 ASK를 포함하지 않는다. 세션의 과거 위험 때문에 동일 업무가 무한 생성되는 것을 막는 조건이 새 불확실성까지 억제한다.

UI 영향:
arena/web/main.js는 완료된 related_task를 받으면 task=null로 두고 관측 입력을 비활성화한다. 새로운 보류 요청에 대해 추가 확인 결과를 기록할 수 없다.

최소 수정:
세션의 과거 위험만 유지하는 ASK와 새로운 현재 턴의 ASK를 구별한다. 입력 지문·사유가 같은 반복은 억제하되 새로운 입력 또는 새로운 원인에는 확인업무 생성·갱신을 허용한다. 자기보고만으로 과거 위험을 해제하는 변경은 필요하지 않다.

수정 후 쌍으로 검사:
- 같은 입력·같은 원인 반복: 업무가 중복 생성되지 않는다.
- 이전 업무 보고 후 다른 입력의 ASK: 새 업무가 열리거나 명시적으로 갱신된다.

범위:
실제 Zoro의 분류 오류를 재현한 것이 아니다. 통제한 Typed 응답을 사용하면서 실제 정책·후처리·SQLite·업무 생성 로직을 실행한 결과다. 증거: code_audit_repro_results.json.

F03 / P0 / 모델이 읽어낸 내용을 후단 어휘 규칙이 막는 실패가 남아 있다

기존 잠금 AI24 사례:
“본인에게 전송된 일회용 확인 코드를 이 메시지의 답장으로 보내세요.”

저장된 모델 출력:
- q_action: otp 0.9704
- q_speech: direct_request 0.7164
- q_current_exposure: yes 0.8869

최종 결과:
ASK_HUMAN / NO_GROUNDED_ACTION_ANCHOR.

원인:
기존 앵커와 신규 exposure_terms에서 “일회용 확인 코드”를 충분히 포착하지 못해, 모델의 민감정보 요청 판단이 구체적 중단 안내로 이어지지 않는다. 이 문제는 이미 V51_FAILURE_ANALYSIS.md에 기록돼 있고 이번 저장 결과 검산에서도 해당 ASK를 확인했다.

영향:
이 사례를 Zoro가 OTP를 이해하지 못했다고 해석하면 모델·추론 개선에 시간을 쓰면서 실제 병목을 남길 수 있다.

최소 수정:
현재 요청 절의 행동·대상 구간을 기준으로 어휘 근거를 검사하는 작은 수정 후보를 만든다. 동의어·복합 금액·금지·인용·복합 요구를 함께 평가한다. 특정 잠금 문장만 예외 처리하거나 전역 threshold 0.70을 근거 없이 낮추지 않는다.

검증:
같은 raw 응답으로 수정 전후 정책을 재생해 어느 조건이 결과를 바꿨는지 확인한다. 그 다음 새 문장으로 실제 Zoro를 호출한다. 기존 AI24는 이제 알려진 회귀·진단 자료로 취급한다.

F04 / P0 조건부 / 최신 서버로 교체하면 endpoint 문자열 변경만으로 연결되지 않는다

현재 ModelClient._check_target()과 Arena의 check_loopback_endpoint()는 /v1/systemone만 허용한다. /v1/decide를 설정하면 네트워크 이전 INVALID_MODEL_ENDPOINT가 재현된다.

2026-11-19 열람한 현재 Zoro 모델 카드는 trida-stack의 /v1/decide와 request·reasoning envelope를 설명하고, fitted temperature는 1.59이다. 공식 Trida Decision 페이지는 /v1/systemone과 2.19를 설명한다. 프로젝트의 과거 검증 기록에는 1.52가 남아 있다.

판단:
현재 팀의 검증된 로컬 서버가 틀렸다는 증거가 아니다. 서로 다른 버전·서빙 경로를 섞으면 장애가 생긴다는 근거다. 새 모델 카드 수치로 기존 온도만 바꾸는 것도 정당화되지 않는다.

최소 대응:
이미 작동한 모델 revision·head·온도·서버·endpoint·11문항 profile을 고정한다. 새로운 서버를 꼭 써야 한다면 요청 envelope와 응답 계약을 처리하는 어댑터를 별도로 만들고 실제 스모크 테스트한다. 모델/서버 교체와 정책 수정은 한꺼번에 하지 않는다.

F05 / P1 / 정상 입력에도 보류 부담이 크고, 보류 후 행동의 종류가 좁다

AI24 후보는 24건 중 ASK 13건, 정상 12건 중 불필요 ASK 5건이다. 적절한 ASK도 있으므로 전부 오류가 아니다. 그러나 정상 사용자에게 돌아오는 확인 부담은 제품 효용에 직접 영향을 준다.

현재 Arena가 실제 업무를 생성·저장하므로 아무 행동도 하지 않는 분류기는 아니다. 다만 확인업무는 INDEPENDENT_CHANNEL_CHECK 한 종류이고 안내문도 공통이다. 모델 장애, 원문 부족, 위험 요청, 과거 위험 유지가 사용자 입장에서 충분히 다른 다음 행동으로 드러나지 않는다.

최소 수정:
모델 장애이면 연결 복구 후 재시도, 원문 부족이면 누락된 요청 대상 확인, 인증정보 요구이면 전달 중단과 독립 확인, 계좌 변경이면 기존 등록 연락처 대조처럼 실제 구현한 범위의 다음 행동을 구별한다. 새로운 외부 연락·지급 자동화가 필수인 것은 아니다.

검증:
보류 사유별로 사용자에게 다음에 무엇을 하라는지 한 문장으로 말할 수 있는지, 선택 후 실제 저장 상태가 달라지는지 확인한다.

F06 / P1 / 위험을 보존하는 장점과 해결을 완료하는 기능을 구분해야 한다

현재 모델은 현재 문장만 읽고, 서버가 prior_pause를 유지한다. 전체 대화를 Zoro가 의미적으로 통합하는 구조는 아니다.

사용자의 확인 보고는 업무 상태를 바꾸지만 위험을 해제하지 않는다. risk_release_implemented=False이며 종료도 CLOSED_UNRESOLVED이다. 사용자의 진술을 외부 기관 인증으로 둔갑시키지 않는 장점이 있다.

다만 “확인 후 안전하게 재개까지 자동 완주”를 주장하면 현재 구현 범위를 넘는다. 정상 사례였다고 확인한 사용자도 현재 상태에서는 검증된 해결로 전환할 경로가 없다.

최소 수정:
이번 제품 목표를 “위험 요청 파악 → 다음 확인업무 생성 → 미확인 사항 보존”으로 명확히 한다. 외부 인증을 실제로 연결하기 전에는 “안전 확인 완료”나 “사기 차단 완료”로 표시하지 않는다. 사용자에게 보관·재개·새 사건의 의미를 설명한다.

F07 / P1 / 근거 표시 성공을 전체 설명 품질로 확대하면 안 된다

기존 보고는 비빈 입력 157건 중 48건에 52개 구간을 표시했다고 기록한다. 그 52개 구간의 원문 위치·문자열 일치가 52/52이다. 이번 검토는 관련 JSON의 집계 산술을 확인했고, 모든 구간의 의미 적절성을 새로 검증하지 않았다.

따라서 “근거 100% 정확”이라고 포괄적으로 소개하면 부정확하다. 표시한 구간의 문자열 일치, 표시 대상 중 표시한 비율, 실제 판단을 설명하는 의미 적절성을 나눠야 한다. 정상 사례의 N/A를 모두 실패로 세는 것도 부적절하다.

시연용 위험 사례는 현재 화자의 요구를 원문에서 정확히 강조하는지 실제 화면으로 확인한다.

5. 원시 자료에서 다시 계산한 결과

자료: data/v51_validation24.jsonl 및 internal/evidence/v51/experiments/stage7_locked_validation24.
라벨 SHA-256은 protocol과 일치했다. 24개 고유 사례, 8 family×3개, 정상 12·위험 7·불명 5개다. 전부 AI_GENERATED이고 independent_eval=false이다.

지표                                      기준선 7문항      후보 11문항
허용된 안내와 일치                         7/24             17/24
전체 ASK_HUMAN                            23/24            13/24
정상 사례의 불필요 ASK                     11/12            5/12
필수 PAUSE_AND_VERIFY 미달                 6/7              2/7
위험·불명 사례의 NO_STRONG_SIGNAL          0                0
정상 사례의 PAUSE_AND_VERIFY               0                0

위 집계와 각 사례 ID 목록은 저장 metrics.json과 모두 일치했다.

중요한 해석:
- 후보의 기대 일치 17건에는 적절한 ASK 6건이 포함된다. “사기 탐지 정확도 70.8%”라는 명칭은 맞지 않는다.
- 후보의 필수 PAUSE 미달 2건은 모두 ASK다. 위험을 정상이라고 통과시킨 2건이 아니다.
- 7문항과 11문항은 질문과 후처리가 함께 달라졌다. 이 비교만으로 “Zoro가 규칙보다 우수하다”는 인과적 기여를 분리할 수 없다.
- 작은 AI 합성셋의 개선은 실제 한국어 사기 일반화 성능이나 피해예방률을 증명하지 않는다.
- 반대로 수치가 조작됐거나 개선이 전혀 없었다고 주장할 근거도 없다.

실행 근거:
원시·정책 결과는 각각 24+24개이며 고유 ID 대응이 일치한다. 저장된 runtime 카운터 1288→1336의 차이 48이 run_summary와 일치한다. protocol에는 모델·head·설정 정보가 있다. raw는 PARSED_NOT_AUTHENTICATED, 결과는 MODEL_RESPONSE_UNATTESTED/model_attested=false이다. 과거 실행을 추적할 근거는 있으나 이번 장비의 현재 모델 인증은 아니다.

지연:
기존 전체 157회씩의 요약은 후보 p50 275.9ms / p95 289.008ms를 보고한다. 이번 확보된 잠금24 부분집합에서 저장 latency_ms를 재계산하면 기준선 p50 149.24ms / p95 155.648ms, 후보 p50 283.255ms / p95 288.0045ms다. 분모가 다르므로 서로 모순이 아니다. 둘 다 과거 warm 요청 기록이며 현재 앱의 사용자 입력부터 최종 작업 표시까지 걸린 시간이나 cold start 결과가 아니다.

6. 창의성을 어디에 둘 것인가

비교 범위는 공식 설명을 확인한 두 제품으로 제한했다.

Google Phone/Pixel Scam Detection은 이미 통화 중 사기 패턴을 탐지해 알림·소리·진동을 주며 경고 무시 또는 통화 종료 조작을 제공한다. “기존은 전화번호 DB만, 우리는 AI 문맥과 행동 개입”이라는 구분은 적절하지 않다. 지원 기기·지역 제한만으로 우리 제품의 성능과 시장성을 입증할 수는 없다.

Eftsure는 계좌·거래처 정보 검증에서 연락처를 독립적으로 확보한 뒤 전화로 확인하는 절차를 설명한다. PAYLOCK의 계좌 변경→독립 확인 자체를 새로운 발명이라고 주장하기 어렵다.

해커톤의 창의성은 세계 최초의 학술 신규성과 같지 않다. 집중할 장면은 다음과 같다.

“위험한 요구가 나온 뒤 상대가 정상적인 말로 바꿔도, 아직 해결되지 않은 요청은 사라지지 않는다.”

추천 제품 한 문장:
“의심계는 메시지 속 위험한 행동 요청을 읽어 다음 확인업무를 만들고, 이후 말이 바뀌어도 미해결 위험을 계속 추적하는 에이전트다.”

경쟁 제품에 동일한 기능이 절대로 없다는 배타적 신규성 주장이 아니다. 현재 코드로 설명·입증할 수 있는 핵심 경험을 선명하게 하는 제안이다.

일반 개인을 위한 문자 확인과 기업 지급 담당자를 위한 PAYLOCK은 구매자·책임·유통 경로가 다르다. 발표 본편에서는 한 사용자와 한 문제를 선택한다. 현행 구현을 기준으로는 의심계 세션 흐름을 본편, 기업 지급 업무는 후속 적용 예시로 두는 편이 자연스럽다. 확인하지 않은 시장 규모·계약 가능성·피해 감소율은 만들지 않는다.

7. 세 가지 시연과 로그

아래는 실행을 요구하는 검증 설계이며, 아직 이 조합의 실제 모델 성공을 보장하는 대본이 아니다. 실제 발표 시간은 현장 공지에 맞춘다.

시나리오 A: 같은 단어, 다른 요청
- 새 세션에서 정상 안내 또는 보호 경고를 입력한다.
- OTP 전달·송금 등의 직접 요구로 요청 부분을 바꾼다.
- Zoro 선택, 최종 정책, 원문 구간, 확인업무 생성의 변화를 보여준다.
- 반례: “송금하라는 요구에는 응하지 마세요”를 무조건 PAUSE로 만들지 않아야 한다.
- 기록: 입력, 요청 ID, model/profile, 현재 턴 행동, 정책 이유, 근거, 전체 완료시간.

시나리오 B: 위험 뒤의 안심 문구
- 직접 위험 요청 후 같은 세션에서 평범한 후속 문장을 입력한다.
- 현재 문장은 NO_STRONG_SIGNAL이어도 세션에는 미해결 위험이 남는 것을 보여준다.
- 사용자 확인 보고, 보관, 재조회, 재개 뒤에도 의미가 바뀌지 않는지 확인한다.
- 새로운 별도 ASK가 발생했을 때 F02 수정 경로도 확인한다.
- 기록: 현재 턴 행동과 세션 행동을 별도 필드로 보존한다.

시나리오 C: 모델 장애와 복구
- 실제 모델 연결을 끊거나 허용된 fault injection을 쓴다.
- 장애를 명시하고 임의 fixture를 실제 Zoro 결과로 바꾸지 않는다.
- 연결을 복구한 뒤 새 요청을 실행한다.
- 이전의 늦은 응답이 최신 입력·세션에 덮이지 않는지 확인한다.
- 기록: 장애 원인·시각, 요청 ID, 실제 복구 후 결과, 작업 상태.

합성 입력 + 실제 Zoro 추론은 함께 가능하다. 입력을 합성했다는 사실과 모델 출력을 재생했다는 사실은 다른 축이다. 로그에는 이를 따로 남긴다.

8. 반례 중심의 가장 작은 추가 실험

목적은 거대한 평가셋이 아니라 현재 실패 원인의 구분이다.

첫째, 같은 의미의 표현 변형: 인증번호 / 일회용 확인 코드 / 휴대폰에 뜬 숫자. 모델 raw와 최종 정책 사이에서 어느 층이 달라지는지 기록한다.

둘째, 같은 위험어의 화행 변형: 직접 요구 / 하지 말라는 경고 / 과거 신고 / 교육용 인용. 단어 존재보다 현재 요청의 주체·대상·부정 범위를 검사한다.

셋째, 복합 요구: 링크 열기와 OTP 전달을 한 문장에 둔다. 단일 q_action에서 확률이 분산돼도 민감 노출 질문과 원문 구간이 적절히 처리되는지 확인한다.

넷째, 상태 전이: 동일 문장 반복 / 새 문장 ASK / 완료 보고 / 새로고침 / 보관·재개. 정확한 판단이라도 다음 업무가 연결되는지 검사한다.

이후 팀원이 새로 작성한 정상·위험·불명 사례를 서로 결과를 보지 않고 주석하고 이견을 기록한다. 기존 AI24는 이미 열람했으므로 수정 후보의 새로운 독립 검증셋으로 다시 부르지 않는다.

Zoro 필요성을 보여주려면 동일 입력·동일 후속 도구에서 간단한 키워드 기준선과 현행 전체 경로를 비교한다. “단순 규칙은 모든 경고문을 오탐한다” 같은 극단적으로 약한 기준선을 의도적으로 만들지 않는다.

9. 상황별 대응과 중단 기준

정상 진행:
- 신호: 실제 요청과 응답·profile 일치, 상태 재조회 일치.
- 행동: 시연 3종을 녹화·로그화하고 기능 동결.
- 유지 기능: 현재 판단, 확인업무, 과거 위험 유지.

모델 서버 계약 불일치:
- 신호: INVALID_MODEL_ENDPOINT, 응답 schema/profile 불일치.
- 행동: 마지막으로 검증한 서버 조합으로 복원하거나 별도 adapter만 검증.
- 중단 기준: 새 서버를 확인하지 못하면 라이브 성공이라고 표현하지 않는다.

모델 응답은 정상이나 최종 ASK 과다:
- 신호: q_action·q_current_exposure는 높지만 anchor/context 게이트 실패.
- 행동: 해당 원문 구간·정책 조건부터 조사한다.
- 중단 기준: 전역 확률 컷오프 하향으로 위험의 정상처리가 늘면 후보를 철회한다.

사용자가 새로운 불확실한 입력을 제시:
- 신호: 현재 턴 ASK인데 열린 확인업무 0.
- 행동: 새 입력/원인에 대한 업무 생성·갱신 규칙을 적용한다.
- 유지 조건: 같은 사건의 무한 중복 생성 방지와 과거 위험 보존.

최신 라이브 실행 불가:
- 신호: 현장 모델 호출 미성공·네트워크/서버 장애 지속.
- 행동: 실시간 실행과 구분해 저장 결과를 재생하고 미검증 범위를 밝힌다.
- 한계: 재생은 설명 보조이며 실제 라이브 검증을 대신 충족하지 않는다.

10. 바로 수행할 순서

1) 최종 시연 진입점, 활성 profile, 서버 조합을 고정한다.
2) F02 새 ASK 후속업무 결함을 최소 수정하고 중복 억제 반례와 함께 확인한다.
3) F03 어휘/절 근거 병목을 작은 후보로 수정하고 정상·경고·인용 회귀를 검사한다.
4) 실제 모델로 정상·조건 변경·장애 복구 시나리오를 각각 끝까지 실행한다.
5) 현재 발표 대본과 README를 실행 상태에 맞춘다.
6) 요구된 저장소·3종 로그·데모를 제출 단위로 묶고 현장 제출 마감·형식을 확인한다.

새 Jev 결합, 로지스틱 계층 승격, 대규모 파인튜닝, NPU 최적화는 현재 병목을 해결한다는 추가 증거가 없는 한 이번 우선순위에서 뒤로 둔다. 효과가 미입증인 v5.2 계층을 비활성화한 판단은 타당하다.

11. 가장 중요한 전제와 반례

전제:
“모델의 선택 확률을 높이거나 해석 계층을 추가하면 에이전트의 최종 행동도 좋아질 것이다.”

반례 질문:
“Zoro가 일회용 확인 코드 전달을 OTP로 0.9704, 현재 노출로 0.8869로 읽었는데도 사전에 해당 표현이 없어 보류된다면, 모델을 한 번 더 생각시키는 것이 어느 부분을 고치는가?”

답:
추가 추론이 다른 사례에 도움 될 가능성은 있다. 그러나 이 저장 사례는 이미 뒤쪽 원문 근거·어휘 조건을 병목으로 가리킨다. 우선 그 조건을 최소 수정하고 정상·부정·인용의 반례를 통과하는지 확인해야 한다. 모든 잔여 실패의 원인이 같다는 뜻은 아니다.

판단을 위한 세 문장:
선택을 맞혔다는 사실만으로 다음 행동이 완성되지는 않는다.
보류를 많이 했다는 사실만으로 유용한 보호가 입증되지는 않는다.
해결했다고 말할 때는 어떤 관측이 무엇을 바꾸었는지 보여줘야 한다.
