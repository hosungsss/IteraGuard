## 0. 1분 요약 및 최종 권고

1. **'응답 멈춤'과 '선택 오류·보류'를 별개 장애로 취급한다.** HTTP 요청·큐·로드·생성·종료 토큰·타임아웃·후처리 중 최초로 실패한 층을 기록한다. `ASK_HUMAN`은 오류가 아니라 명시적 보류일 수 있다.
2. **0.75 대 0.667은 두 경쟁 가설로 검토한다.** 선택지 4개인 같은 질문의 최고 확률 0.75를 kev 공식 confidence 식 `(pmax-1/K)/(1-1/K)`에 넣으면 0.6667이다. 별도 q_speech 확률이라는 증거는 아직 없다. 다른 가능성으로, `dmsg/prototype/model_bridge.py`는 `q_action` 최고 확률뿐 아니라 `q_speech` 최고 확률도 각각 0.70 이상이어야 기존 경로의 자동 판단을 진행한다. 따라서 `p_action=0.75`, `p_speech=0.667`이면 `MODEL_LOW_CONFIDENCE_OR_AMBIGUOUS` → `ASK_HUMAN`이 나올 수 있다. **이는 실제 통화 사례의 원인으로 확정된 것이 아니라, 재현 가능한 코드 경로다.**
3. **수학적 확인:** `0.667 < 0.700`이다. 통화의 “0.667이 0.7 이상”이라는 진술은 수치상 성립하지 않는다. `컴피턴스`가 confidence인지, 다른 지표인지, 음성 전사 오류인지는 별도 확인이 필요하다.
4. **Jev 직접 병합은 우선순위 최하위.** Zoro-1은 이미 `noul`·`choice`·`score`의 Typed Decision 헤드를 포함한다. Jev는 TypeSafe의 별도 호스팅 모델이며, 오픈 프로젝트 `kev`는 서빙/형식/평가 하네스다. 세 주체를 동일시하거나 Jev가 Zoro-1의 '선택 장애 제거 장치'라고 확정하지 않는다.
5. **CPU 전환은 장애 해법이 아니다.** CPU도 SIMD·멀티스레딩·병렬 실행을 하며, CPU/GPU 어느 쪽이든 로직 오류, 잘못된 종료 조건, OOM, 토큰 한도, 데드라인 초과가 생긴다. CPU가 느려지는 비용부터 검토하고 동일 입력·동일 checkpoint에서 장비 차이를 통제해 시험한다.
6. **추론을 더 오래 돌리면 자동 개선된다는 가정 역시 기각.** 공식 Zoro-1 자료에서도 추론 후 특정 과제는 향상되지 않거나 오히려 악화한다. `</think>` 정상 종료, 토큰 한도, 추론 전후 정책 영향, 별도 보정을 확인한다.
7. **v5.2의 5특징 로지스틱 회귀는 실험 도구로 유지한다.** AI 작성 합성 개발자료 61건에서의 교차검증 Brier는 실사용 성능 증거가 아니다. 모델의 확률을 오즈로 변환했다가 다시 원복하는 것은 독립 검증이 아니다.
8. **14일 토요일 회의(2026-11-14)의 우선 의제:** A. 실제 오류 로그 3종(선택/보류/서버 정지), B. 공식 모델·외부 API 사용 가능 범위 및 현장 GPU, C. 의심계의 단일 시연 경로/백업 패키징. 사용자가 제공한 통화에서 제안된 두 의제(오류·패키징)를 구체적인 실험/산출물로 전환한다.

### 1.3 숫자·표본의 정확한 의미

Drive의 v5.1 `LATEST_VERSION.json`은 `DEVELOPMENT_CANDIDATE`, 패키지 764파일/137,162,354바이트/해시 `72a59c5d...3624f`를 기록한다. 이 대화에 업로드된 `[v5.1]` ZIP은 **153,902,391바이트/876항목**으로 다른 물리적 아카이브다. **두 ZIP이 동일한 파일이라고 단정해서는 안 된다.** 내용/패키징 범위 차이가 있을 수 있다. 업로드 ZIP 자체 SHA-256은 이전 v5.2 장부에 `b7aa499b...03bbb1`로 기록되어 있으나 현 작업에서 경로별 비교가 더 필요하다.

v5.1의 자체 기록은 잠금 **AI 합성 24건**에서 기존/후보 기대 안내 일치 **7→17**, 정상 불필요 `ASK_HUMAN` **11→5 (정상 12건)**, 필수중단 미달 **6→2 (필수중단 7건)**이라고 보고한다. 이 수치는 **이번 문서에서 새로 실모델을 호출한 결과가 아닌 당시 저장 실험 결과**이며, 사람의 독립 평가·실세계 사기 예방 성능을 의미하지 않는다. 기존 정책이 누락을 `ASK_HUMAN`으로 보내는 경우는 안전 보류지만, 목표 `PAUSE_AND_VERIFY` 달성은 아니다.

## 3. 네 선택지 0.75 / 컴피턴스 0.667 사례를 해부한다

### 3.1 동일한 ‘확률’이 아니다

서로 구별해야 하는 양:

- `pmax_choice = max(P(choice_i | state, question))`: `choice` 질문의 최고 선택지 확률.
- `pmax_speech`: 별도의 `q_speech` 질문에서 최고 화행 확률.
- `p_yes_noul`: 특정 명제에 대한 yes 추정치. **일반 확신도나 실제 사기 확률과 다르다**.
- `pmax_noul = max(p_yes_noul, 1-p_yes_noul)`: 예/아니오 답의 최고 선택 확률.
- kev choice confidence = `(pmax-1/K)/(1-1/K)`: 최고 선택확률과 다르다. K=4, pmax=0.75이면 0.6667이다. 음성 전사의 competence가 이 필드를 의미하는지는 원시 응답으로 확인해야 한다. entropy와 margin도 별도 지표다.
- `p_domain_event`: 위험행동 요청 같은 **명시적으로 라벨 정의된 사건**의 외부 보정 확률. 아직 현행 제품에서 독립 보정된 실세계 사기 발생 확률은 없다.

**v5.1 실제 코드 경로(직접 확인):**

```python
# dmsg/prototype/model_bridge.py - 판단 게이트의 핵심 부분(구조만 간추린 설명)
p_a = normalized['q_action']['probabilities'][a]
p_sp = normalized['q_speech']['probabilities'][sp]
if contextual_conflict:
    action = ASK_HUMAN
elif p_a < threshold or p_sp < threshold or a == 'unclear' or sp == 'unclear':
    action, reason = ASK_HUMAN, 'MODEL_LOW_CONFIDENCE_OR_AMBIGUOUS'
```

따라서 **가상의** `p_a=0.75`, `p_sp=0.667`, `threshold=0.70`의 경우 결과는 보류다. v5.1 `integration/v51_policy.py`에는 11문항 의미 게이트·현재성·어휘 앵커·우선순위도 별도로 존재하여, 하나의 최고 확률만으로 결과를 예측할 수 없다.

**반증 테스트:** 같은 응답 JSON의 복제본에서 `q_speech`의 선택확률을 0.71로 바꾸되 나머지 선택지에 잔여 확률을 재배분하여 합 1을 유지하고 다시 정책을 실행한다. 결과가 바뀌면 이 고정 사례에서 해당 값에 대한 정책 민감도가 확인된다. 실제 모델 개선이나 일반적인 필요조건이 증명되는 것은 아니다(단, 전체 후보 정책에서 다른 조건도 있어 결과를 보장하지 않음). 기존 원본을 수정하지 않은 복제 fixture에서만 한다.

### 3.2 공식 Zoro-1의 ‘추론 호출 0.7’과 제품의 ‘보류 0.7’은 별개

공식 모델 설명은 **질문 하나라도** 최고 선택지 확률이 기준 아래면 요청 단위로 추가 추론을 고려하는 *reasoning escalation*을 제시한다. 제품의 기존 0.70은 `q_action`·`q_speech`의 보류·판단 게이트다. 숫자가 우연히 같아도 운영 의미와 비용이 다르다. 현재 `0.7`을 모든 기능의 단일 글로벌 컷오프로 재사용하는 방식은 금지한다.

- `τ_reason` = 추가 생성/재판정 여부를 판단할 개발셋 가설 기준(예: 0.7, **보정·효익 검증 필요**).
- `τ_legacy` = 현재 v5.1 행동·화행 확률에 적용되는 **동결된** 정책 기준(0.70).
- `p* = C_FP/(C_FP+C_FN)` = (이진 경고/통과와 동일 단위 비용·사건 확률이 정의됐을 때만) 기대 손실 비교에서 유도되는 **행동** 임계값.
- `ASK_HUMAN`을 세 번째 행동으로 추가하면 별도의 검토 비용·지연·최종 결과를 포함해 **3행동 기대 효용**을 비교해야 한다. 위 p*를 그대로 사용하면 안 된다.

**중요:** `q_scam.yes=0.8`을 `p(real-world fraud)=0.8`로 간주하고 p*에 넣는 것은 부적절하다. 모델 출력 명제, 평가 라벨 및 보정 목표가 다르다.

### 3.3 소스에 이미 기록된 독립적 오류 사례

`docs/V51_FAILURE_ANALYSIS.md`는 다음 종류의 반례를 구체적으로 기록한다.

- 송금 행동 모델 확률은 높지만 “2천만 원” 표현을 기존 정규식이 놓쳐 정책 앵커가 실패한 사례.
- `q_action`이 OTP/링크/원격 설치 사이에 확률을 나누어 가지므로 직접 요청을 감지해도 한 개 행동의 최고 확률이 0.70을 넘지 못해 보류한 사례.
- `q_action=none`이 0.93으로 높지만 `q_speech`가 인용과 서술 사이에서 갈려 보류한 정상 메시지.
- 이전 PAUSE를 유지하는 안전 정책 때문에 정상 결제에 대한 과잉 중단까지 계속 유지되는 사례.

**의미:** 문제 일부는 Zoro 신경망이 아니라 **단일 라벨 정책·문맥 앵커·다중 질문의 논리적 AND·보존 정책**에서 발생한다. 따라서 Jev 모델을 바꾸거나 추가하기 전에 구현 수준의 반례를 최소 수정으로 해결할 수 있는지 확인한다.

## 4. ‘응답 중 멈춤’에 대한 최초 오류 지점 분석

### 4.1 6가지 독립적인 장애 계층

| 층 | 실패 후보 | 관측할 신호 | 해결 우선순위 |
|---|---|---|---|
| 1 입력·클라이언트 | 잘못된 endpoint, 4초 타임아웃, API 규격/모델명 오류 | 요청 ID/URL/timeout/HTTP status/헤더/요청 JSON 지문 | P0 |
| 2 큐·동시성 | GPU 메모리 경합, 누적 큐, 요청 중복·역순 | queue_ms, concurrency, batch, 429/503 | P0 |
| 3 모델 로드/자원 | 모델 cold start, RAM/VRAM 부족, KV/토큰 한계 | 로드 시간, OOM/kill, peak RAM/VRAM | P0 |
| 4 Typed prefill/헤드 | 체크포인트/포인터 헤드 불일치, 선택지/모드 오류 | 모델 SHA, head SHA, schema, normalization 오류 | P0 |
| 5 선택적 생성 추론 | `</think>` 미도달, 최대 토큰 절단, 무한 재질문 | finish_reason, generated_tokens, token budget, reasoning mode | P0 |
| 6 후처리·상태/UI | 조용한 JSON 파싱 실패, stale UI, 보류를 실패로 표시 | `model_response` vs `policy_action`, session_version, audit trace | P0 |

**확인된 현행 코드:** `dmsg/prototype/model_bridge.py`의 `ModelClient`는 환경변수 `DMSG_MODEL_TIMEOUT_S`의 기본 **4.0초**를 사용하며, `model_attested=False`를 명시한다. 실제 모델 서버의 지연·콜드스타트에 비해 4초가 짧을 수 있다. 이 설정은 **장애 후보**이지 제보 사건의 실제 원인이라고 확정할 수 없다.

**우선할 관측 계약:** `request_id`, `input_sha256`(원문 자체 비저장), `checkpoint_commit`, `head_sha256`, `temperature_source`, `profile_hash`, `policy_hash`, `queue_ms`, `prefill_ms`, `generation_ms`, `http_status`, `finish_reason`, `max_tokens`, `response_parse_status`, `reasoning_truncated`, `pmax_per_question`, `policy_action`, `policy_reason`, `wall_latency_ms`, `timestamp_utc`. 개인정보·실제 악성 URL 원문은 감사 로그에서 최소화.

### 4.2 CPU/GPU 가설의 타당성

- **사실:** CPU와 GPU 모두 병렬 계산을 수행할 수 있다. GPU 병렬성 자체가 응답 중단의 원인이라는 증거는 없다. 동일한 로직은 CPU에서도 타임아웃/무한 루프/OOM으로 실패할 수 있다.
- **추론:** CPU는 GPU에 비해 4B급 모델의 실제 토큰 처리 속도가 느릴 수 있고 기기별 메모리 대역폭이 큰 영향을 준다. GPU→CPU 이전은 문제 해결 이전에 성능/메모리/대기 시간을 악화시킬 수 있다.
- **실험:** 같은 정확한 모델 checkpoint, `kev` export, 정밀도, 토큰 수, 입력 및 추론 파라미터를 고정해 CPU vs GPU 각각 cold/warm/동시성/추론-종료 테스트를 한다. 여기서 동일성은 모델·입력 계약 수준이며 부동소수점 bitwise 완전 일치는 기대하지 않는다. CPU fallback은 별도 장애 회복 경로로만 채택한다.

### 4.3 타임아웃 설계

권장안은 **무한 대기/무한 반복이 아니라** 다음 상태기계다.

`CREATED → QUEUED → RUNNING_DIRECT → (READY | NEED_REASONING | ERROR)`  
`NEED_REASONING → RUNNING_REASONED → (READY | TRUNCATED | TIMEOUT | ERROR)`  
`TRUNCATED/TIMEOUT/ERROR → (BOUNDED_RETRY if safe and transient) → REVIEW_REQUIRED or SAFE_FALLBACK`

- Connect/queue/direct/reasoning/UI **서로 다른 예산**을 둔다. 실제 p95/p99를 측정한 뒤 결정하며 검증되지 않은 초 단위 수치는 설정값으로 고정하지 않는다.
- `429`/일시적 `503`/네트워크 절단 등 적절한 경우만 제한적으로 재시도; schema mismatch, 허위 모델 ID, 권한 오류, 잘린 생각을 그대로 재사용하는 재시도는 금지.
- 고위험 외부 행동은 재시도해도 실행되지 않도록 **권한 게이트·멱등성 키**를 분리한다. 모델 응답을 기다리며 은행·SMS·APK를 실행하지 않는다.
- 1회 추론 확장은 **상한을 두고** 정상 종료와 결과가 확인된 경우에만 재판정한다. 사고가 끝나지 않았는데 512 토큰에서 강제 종료하면 품질이 더 나빠질 수 있으며, 공식 카드에는 최소 4,096 토큰 권고가 있다. 자원 부족으로 그 예산을 보장 못하면 추론 모드를 끄고 인간 확인을 사용한다.
- UI는 `QUEUED`, `ANALYZING`, `VERIFYING`, `HUMAN_REVIEW`, `UNAVAILABLE`을 정확히 구분한다. 진행률을 꾸며내지 않는다. timeout 이후 실제 계산이 지속되는지, 서버가 작업을 취소했는지 확인·수명 종료를 기록한다.

### 5.2 기본 권고

1. **Jev 직접 weight fusion은 하지 않는다.** 존재하지 않는 호환 레시피를 전제하지 않는다.
2. Jev API를 쓰고 싶다면 반드시 사용자 승인·대회 운영진의 허용·라이선스/과금·개인정보 전송 동의와 데이터 처리 검토를 통과한 **독립한 benchmark arm**으로 둔다.
3. 논문·팀 자료의 좋은 아이디어는 미들웨어에서 개별 기능 계약으로 옮기되, 코드와 원문을 무단 재배포하지 않는다.
4. **대회 데모의 핵심은 Zoro-1이 실제 어떤 필수 판단을 했고, 이를 제거하면 어떻게 달라지는가**이다. 외부 모델이 실질 판단을 대체하면 Track 1의 모델 기여 설명이 약해질 수 있다.

### 6.1 질문 분해 방법

**좋은 방식:** 한 질문은 그 질문만으로 답할 수 있는 사실 조건 하나를 검토하고, 모델이 알 수 없는 발신자 인증 정보는 하네스에서 직접 확인한다. 예:

- `Q_action`: 현 발화가 **현재 수신자**에게 요청하는 직접 행동은 무엇인가? `송금/인증정보/앱 설치/외부 메시지 이동/기타 요청/없음/불명확`.
- `Q_speech`: 그 표현이 현재 직접 요청/간접 유도/경고·부정/인용·과거 보고/정보 제공/불명확 중 무엇인가?
- `Q_sensitive_exposure`(noul): 현 발화가 인증정보·개인정보를 제공하도록 **요구**하는가? 단순 언급은 아님.
- `Q_payment_change`(noul): 현 발화에 **등록된 지급 계좌를 변경하고 송금하라는 제안**이 명시됐는가? (실제 등록 사실은 다른 증거로 검사).
- `Q_evidence`: 위 답이 명시적 문장 근거로 지지되는가? 모델의 자체 판단은 독립 사실이 아님.

**함정:** 다중행동 입력을 한 개 `choice`로 억지 선택하면 `OTP`·`링크`·`원격 앱`에 확률이 나뉘어 각각 0.7을 못 넘을 수 있다. 이때 행위별 독립 `noul`로 병렬 탐지하거나 상위 `민감 요청 여부`→하위 상세 분류의 **계층적 구조**를 비교하되, 질문끼리는 서로 답을 볼 수 없으므로 하네스가 결합한다. `noul` 여러 질문의 yes 값은 합쳐서 1이 되는 선택분포가 아니다.

**보안:** 원문 속 `SYSTEM:` 같은 문구와 개인 정보는 외부 데이터로 표시하고 시스템 명령으로 해석하지 않는다. 모델 출력은 실제 송금·SMS 삭제·URL 방문 권한을 갖지 않는다.

### 6.2 통계적 보정/5특징 로지스틱의 올바른 위치

v5.2 실험의 5특징은 `q_scam.yes`, `q_pressure.yes`, `q_current_exposure.yes`, `q_payment_anomaly.yes`, `q_request_scope.sensitive_request`다. 기존 AI 합성 개발자료 **n=61, family=37**, 그룹 5분할 OOF Brier **0.1120**, 원본 `q_scam` 대비 단순 진단 Brier **0.1103** 기록이 있다. 그러나 두 신호의 의미와 타깃 라벨이 다를 수 있어 **우월성 지표가 아니다**. 원본 통화의 오즈비 역분석도 `posterior odds → posterior probability`가 수학적으로 일치하는지 확인할 뿐 **같은 데이터로부터 새 관찰을 생성하지 않는다**.

유효한 다음 실험은: 독립 인간 라벨(최소 2인 이견 조정) → 사건 패밀리 완전 분리 → 개발셋에서 계수·특징·임계값 **단 하나** 선택 → 새로 확보한 잠금 평가셋에서 Calibration·Brier·FPR/FNR/abstention/비용·p95 → 개선이 불명확하면 NO CHANGE. 모델 입력에서 계좌·발신자 진위를 확인한 사실을 추가한다면 그것은 신경망 출력이 아니라 독립 근거임을 표시한다.

### 6.3 추가 추론 VOI 실험

같은 사건의 직접 결과/추론 후 결과를 비교하되, 추론 전후의 실제 **정답 라벨과 정책 행동**을 함께 측정한다. 모델이 높은 확률을 갖게 됐다는 것과 더 적절한 경고가 나온다는 것은 다르다.

- 이득: 위험 `PAUSE` 누락 감소 및 정상 `ASK/PAUSE` 감소, 비가역 행동 차단 품질.
- 비용: 지연 p50/p95, GPU 메모리/전력, API 요금·실패 비율, 사람 검토 비용.
- 선택 기준: 비용을 동일한 효용 단위로 환산하고 `E[loss_direct]-E[loss_reasoned]-cost_reasoning > 0`을 **독립 잠금 자료에서** 확인.
- `max_prob < 0.7`은 **실험 시작점**이지 자동 최적 규칙이 아님. 직접·추론 모드에 각각의 온도를 별도 검증하며 출력 분포에 무심코 온도를 두 번 적용하지 않는다.
- 원문이 길어 추론이 한도를 초과하는 경우는 별도 실패 모드로 집계한다. 정상 종료하지 못한 추론은 판정의 근거로 재사용하지 않는다.

### 7.1 실험 Arm

| Arm | 구조 | 검증 질문 |
|---|---|---|
| A0 | v5.1 활성 정책·11문항 기본값(동결) | 현재 누락·과보류·과중단·실행비용은? |
| A1 | A0 + 관측 로그/오류 상태 분리(판단값 불변) | 같은 증상을 재현 가능하게 찾는가? |
| A2 | A1 + 개발셋에서 하나 선택한 원자형 질문 후보 | 실제 뜻 구분이 나아지는가? |
| A3 | A2 + 독립 코드 게이트 최소 수정 | 필요한 경고와 정상 안내가 함께 개선되는가? |

**기여 분리:** 누적 A0~A6 외에 동일 기준선 대비 질문만 변경/정책만 변경/둘 다 변경하는 비교를 둔다.

**결정론적 기본값:** 어느 arm도 v5.1 기본 정책을 시험 중 자동 교체하지 않는다. 양성/음성 계약 테스트와 완전히 별도의 잠금 평가셋을 통과한 뒤 승인 게이트를 연다.

### 7.2 평가 데이터·지표

최소 시나리오 패밀리: (a) 직접 고위험 요청, (b) 간접 연락 유도, (c) 정상 공지, (d) 정상 예약·결제, (e) 인용/신고, (f) 부정/경고, (g) 복수 행동, (h) 기관 사칭 주장, (i) URL·APK 미확인, (j) 정상 고객이 권유하는 비민감 행동, (k) 서버 장애/시간초과, (l) 역순/중복/재시도. 모든 패밀리에서 표면 문구·기관명·금액·상대방을 변형하고, **같은 원문·시나리오·생성 템플릿에서 파생된 유사 사례 그룹을 개발·잠금에 나누지 않는다**. 경고/인용 같은 넓은 의미 범주 전체를 하나의 그룹으로 취급하지 않는다. 표본 간 의존성이 있으면 그룹 단위 bootstrap을 적용한다.

- **주 지표:** 필수 PAUSE 이행률(ASK는 별도), 위험 누락률, 정상 false PAUSE, 불필요 ASK, 경고 정밀도, 판단 보류율.
- **보정:** 정해진 이벤트 라벨의 Brier/ECE/신뢰도 다이어그램. `q_scam`을 실사기 확률로 교정하지 않았으면 해당 명제 정확도만 보고한다.
- **성능:** model-only/전체 end-to-end p50/p95, 오류율·timeout·cold/warm, 메모리 및 동시성.
- **통계:** 사건 단위 짝지은 bootstrap 또는 적절한 McNemar, 95% 구간과 분모. 동일모델의 3번 반복은 독립 표본 수 3배가 아니다.
- **제거 실험:** 미들웨어 사전 정규화, 질문 분해, 임계값, 후단 정책, 추가 추론, 외부 모델을 하나씩 제외하여 순기여를 확인.
- **설계 선행:** 최소 허용 수치와 실패 시 되돌릴 조건을 개발 실험 전에 합의한다. 수치를 임의로 “일반 95%”처럼 만들지 않는다.

### 7.3 승격 게이트 및 거부조건

`PROMOTION=GO`는 독립 평가에서 주요 위험 누락의 개선, 정상 과보류/과중단 비악화, p95·비용 예산 충족, 출처·모델·정본 인증, 실제 Zoro-1 Typed 기여 및 기존 기능 회귀 없음 **모두** 충족 시에만 가능하다. 실제 모델 미연결·human test 미완료·정본 없음·외부 API 약관 불명·Android 실기기 미검증을 자동 PASS로 승격하지 않는다.

기본 판단은 **NO CHANGE**. 판정 성능 문제로 정책을 바꾸되 그 정책의 유일한 검증 데이터가 이미 공개된 AI24라면 결과는 **EXPLORATORY**, 출시 승인 불가.

### 8.1 4D Ontology

- **구조:** SMS/발화(비신뢰 입력), 발신자 주장, 실제 인증된 발신자/기관, 질문·선택지·모델·포인터 헤드, 응답확률, 독립 사실, 정책, 사용자 행동, 감사·복구. 연결 종류를 `asserted_by`, `observed_by`, `inferred_by`, `validated_by`, `authorized_by`로 구분.
- **시간:** 메시지 수신→정규화→직답→선택적 추론→재판정→사용자 안내→기관 독립 확인→상태 갱신의 일련 시점과 `request_id`·revision·서버 cold/warm·out-of-order 이벤트 기록. 이전 보류는 늦은 결과만으로 자동 해제 불가.
- **관점:** 잠재 피해자(놓침 손실), 정상 발신자/거래 담당자(과잉 경고 비용), 팀 개발자(하드웨어 및 시간), 심사위원(실제 지정모델 기여), 개인정보 주체(원문/외부 API 전송 위험).
- **방향/역검증:** 입력→질문→Typed raw→정규화→게이트→UI/확인업무와 역순으로 UI 사유→규칙 ID→원래 응답/증거→요청·모델 매니페스트를 추적. `pmax` 숫자만으로 독립 사실 검증이 되지 않음.

### 8.2 NPU 경계

이번 통화와 현재 검토에서 **실제 NPU 실행/프로파일러 근거는 없다(NOT_RUN)**. Android KoELECTRA의 온디바이스 경로와 외부 GPU Zoro-1 4B 모델을 구분한다. 특정 NPU 가속의 가치가 필요할 때만 동일 모델·가중치·정밀도·입력에 대해 CPU/NPU 실제 실행 사업자와 정확도·지연·전력·발열을 측정한다. **서버의 GPU→CPU 전환을 NPU 최적화라고 부르지 않는다.**

## 10. 무엇을 '우승 요소'로 제시할 것인가

**과도하게 주장하지 않을 것:** “확률 보정해서 실제 사기 확률을 완벽하게 구했다”, “Jev를 넣어 Zoro의 모든 선택 실수를 없앴다”, “CPU는 멈추지 않는다”, “Zoro 0.75면 무조건 판단해야 한다”, “테스트 100% 통과면 실전 안전”.

**증거가 있을 때의 실제 차별성:**

1. 동일 Zoro-1 Typed Decision을 사용하는 **관측·수명주기 하네스**로 API 오류·보류 이유를 분리했다.
2. 질문 원자화/가드레일이 직접·인용·부정·간접 요청 간 오류를 줄였다(**증거 분모 필수**).
3. 독립 기준선 대비 위험 누락 감소와 정상 과보류 감소를 **동시에** 측정했다.
4. 불확실하면 보류하고, 검증된 외부 사실이 들어오면 상태를 갱신하는 **관찰→판단→안전 행동→확인→감사 폐루프**를 보여준다.
5. 심사위원이 직접 입력한 새 사례에서도 재현하고, 서버 장애시 임의의 가짜 Zoro 응답을 보이지 않는 **정직한 복구 경로**를 보유한다.

공식 2026-11-12 기준 대회 페이지의 Track 1은 Trida Decision Model을 활용하는 Zoro-1 Arena, **공개된 심사 포인트는 창의성**, 세부 조건은 행사 당일 발표다. 주최 측의 '모델 직접 변경/외부 Jev API' 허용을 단정하지 않는다. [공식 페이지](https://hackathon.trillionlabs.co/).

> **권고:** 제보된 0.75/0.667은 “Zoro가 잘못 선택했다”는 결론보다, **서로 다른 확률/정책 게이트를 혼동했을 가능성이 높은 증상**이다. 먼저 실제 요청·응답·상태를 재현하고, 보류와 서버 중단을 구분한다. Jev 직접 병합과 GPU→CPU 단순 전환은 **채택 보류**한다. 질문 분해, 기존 Zoro-1 헤드 검증, 후단 독립 정책, 유한한 추론/서버 복구를 먼저 고도화한다. 개선이 독립 사람·잠금 데이터와 실측 지연/비용에서 입증되지 않으면 **NO CHANGE**한다.

## 14. 현재 선택·정책·UI 진단 계약

- 동일 질문의 pmax/confidence와 서로 다른 질문의 확률을 먼저 구분한다.
- 원시 선택이 존재하면서 ASK_HUMAN이면 정책 사유와 다음 확인 행동을 표시한다.
- UI에서 행동 선택 확률·발화 유형 선택 확률을 별도로 표시한다. `확신` 단일 표기를 사용하지 않는다.
- 이전 위험 보존은 현재 문장 판단과 구별하며 사용자 자기보고로 자동 해제하지 않는다.
- 기존 11문항/0.70/정책 가중치/모델은 유지한다. 표본 검증 없는 임계값 완화는 하지 않는다.
- 지연/서버 장애와 현재 응답 후 보류를 별개로 기록한다.
- 공식 confidence 수식: https://github.com/jaredpalmer/kev/blob/main/kev/api.py (변경 가능한 main 기준, 2026-11-12 열람).
