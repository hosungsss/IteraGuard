# 의심계 제품 요구사항 명세

**제품:** 의심계 Doubt Meter Safety Gate / 스킬 식별자 dmsg  
**문서 버전:** v3.3 검토안  
**기준일:** 2026-11-02  
**동반 문서:** [DMSG_SYSTEM_PROMPTING_v3_3.md](DMSG_SYSTEM_PROMPTING_v3_3.md)  
**기준 자료:** 사용자 첨부 「System Prompting v3.2 — 의심계」 PDF, 본문 9페이지  
**문서 상태:** 구현·검토 가능한 요구사항 제안. 팀 승인·실제 구현·모델 연결·테스트 통과를 의미하지 않는다.

## 1 목적과 제품 결정

의심계는 합성 대화에서 사용자가 요청받은 행동을 식별하고, 원문 근거와 코드 정책에 따라 독립 확인을 안내하는 해커톤용 훈련 아레나다. 발신자의 실제 신원이나 범죄 여부를 판정하지 않는다.

제품의 핵심 단위는 위험 점수가 아니라 **행동 요청과 그 근거**다. 모델은 제한된 분류 결과를 제안하고, 서버 코드가 원문·문맥·세션 상태를 검증한 뒤 고정 안내를 선택한다. 사용자에게 안내를 표시하는 것이 P0 행동이며, 실제 금융·통신 서비스를 조작하지 않는다.

**제품 루프:** 합성 입력 → typed 분류 → 근거 검증 → 정책 → 안내 및 확인 의도 기록 → 후속 턴 → 재평가.

안내 표시 완료, 사용자의 확인 의도, 독립 경로 확인의 자기 보고, 실제 신원 검증은 서로 다른 사건이다. 본 MVP는 앞의 두 사건을 제공하고, 자기 보고를 받더라도 실제 기관 확인이나 위험 해소로 인증하지 않는다.

## 2 원문 유지 사항과 보완 범위

유지: L0~L5 계층, 5개 질문 ID와 허용 라벨, 네 가지 정책 상태, 고정 소비자 문구, 합성 대본, 근거 오프셋 검사, 실모델/모사 구분, 공동 개발 원칙.

보완 제안: 직접 요청·인용·부정의 구분, 여러 위험 행동 동시 등장, 이전 턴 위험의 보존, `evidence_sufficient`와 코드 검증의 구분, 모델 실패 시 분기, 스키마·오프셋·버전·멱등성·로그 계약 및 R01~R14 추적.

원문의 실제 `policy.py`, `TEMPLATES`, `PROMPTS.md`, 테스트 로그는 이번 첨부에 포함되지 않았다. 따라서 아래 우선순위와 수용 기준은 원문을 구체화한 **검토안**이며 기존 코드와 같다고 단정하지 않는다. 특히 원문이 요구하는 L1/L2 변경 승인과 기존 정책 보존 원칙은 구현 변경 시 확인한다.

## 3 사용자와 주요 시나리오

| 사용자 | 필요 | 제공 결과 |
|---|---|---|
| 아레나 체험자 | 어떤 요청 때문에 확인이 필요한지 이해 | 짧은 안내, 검증된 인용, 독립 확인 선택지 |
| 심사위원 | 임의 입력과 상태 변화를 검증 | 입력 수정, 모드 표시, 근거·정책·턴 타임라인 |
| 개발·평가 담당자 | 모델·정책·실패를 분리해 재현 | trace, 스키마/프롬프트 버전, 골든 테스트, 실행 근거 |

### 대표 경로

1. 기관 신분 주장만 존재: 유효한 분류와 코드 검증에서 위험 요청이 없으면 `NO_STRONG_SIGNAL`. 안전 보증 문구는 사용하지 않는다.
2. 같은 세션 다음 턴에 명시적 송금 요구 등장: 코드가 직접 요청과 원문을 검증하면 `PAUSE_AND_VERIFY`. 기관 신원은 계속 미확인이다.
3. “OTP를 알려주지 마세요”라는 경고: 단어 등장만으로 OTP 제공 요청으로 처리하지 않는다.
4. 가짜 SYSTEM 문장: 데이터로 처리하며 은행 동결·코드 실행이 발생하지 않는다. 모델 유효성은 별도로 검사한다.
5. 모델 실패: 독립적으로 검증된 명시적 고위험 요청이 있으면 중단·확인 안내, 그 외에는 `ASK_HUMAN`. 모델 실패를 정상 분류로 기록하지 않는다.

## 4 범위와 제외 사항

### P0

- 사람 검토를 거친 합성 대본 및 수동 텍스트 입력.
- 최신 caller 턴 중심 분류와 최근 최대 3개 턴의 제한된 문맥.
- 5개 닫힌 질문, 분류 어댑터, 근거·화행 검증, 결정론적 정책.
- 고정 문구 표시, 독립 확인 선택지, 확인 의도 기록, 후속 턴 재평가.
- 세션 버전, 오래된 응답 거부, 멱등성, 최소 감사기록, 모드 표시.
- 정상·위험·인용·부정·인젝션·오류·순서 역전 검증.

### P1

- 검증된 실제 endpoint에서의 선택적 Reason-then-Decide 실험.
- 개발/검증/잠금 평가 세션 비교와 지연·보류율 대시보드.
- 접근성 사용성 평가. 고령 사용자 이해도는 실험 전까지 목표다.

### 제외

실제 계좌 동결·송금 차단·통화 종료·SMS 발송·연락처 접근·OTP 및 가족 비밀 수집·실통화 녹음·음성 딥페이크 탐지·신원 인증·실제 피해 감소 효과 주장. Factory CPR·범용 SRE·PAYLOCK 통합은 이 문서의 P0가 아니다.

## 5 기능 요구사항과 수용 기준

R01~R14는 원문에서 참조하지만 정의되지 않은 식별자를 이번 문서에서 구체화한 것이다. 기존 별도 PRD의 동일 ID와 자동 대응한다고 가정하지 않는다.

| ID | 우선순위 | 요구사항 | 관찰 가능한 수용 기준 |
|---|---|---|---|
| R01 | P0 | 입력과 신뢰 경계 검증 | 역할·ID·버전·길이 오류 거부. 대화 안 SYSTEM/JSON/URL에 실행 권한 없음 |
| R02 | P0 | 5개 typed 질문 계약 | 질문 집합·타입·라벨·분포 검증. 미지원 wire 형식은 INVALID |
| R03 | P0 | 직접 요청과 주장 구분 | 신분 주장만으로 위험 요청을 생성하지 않음. 인용·부정는 직접 요청과 구별 |
| R04 | P0 | 코드 기반 근거 검증 | 원문 substring과 offset 일치, 최신 턴·화자·직접성 검사. 실패 근거 미표시 |
| R05 | P0 | 결정론적 정책 | 네 enum만 반환. 독립 고위험 근거가 모델 none보다 우선. 실패 시 근거 없으면 ASK_HUMAN |
| R06 | P0 | 고정 사용자 문구 | 템플릿 버전과 문구가 일치. 안전 보증·사기범 확정·실제 제어 완료 표현 없음 |
| R07 | P0 | 세션·재평가·멱등성 | 늦은 응답이 최신 상태를 덮어쓰지 않음. 동일 재요청은 동일 효과, 충돌은 거부 |
| R08 | P0 | 모드와 모델 상태 공개 | FIXTURE/SURROGATE/UNATTESTED/REAL_ZORO와 INVALID/UNAVAILABLE 구분 |
| R09 | P0 | 원문 보존 최소화 | 세션 종료 후 서버 원문·브라우저 원문 폐기. 기본 로그에 원문·인용·전화번호 없음 |
| R10 | P0 | 합성 아레나와 데이터 분리 | 정상/위험 균형, 시나리오 패밀리 split, 모델 입력에 정답·기대 행동 없음 |
| R11 | P0 | 오류·자원 제한 | timeout/잘린 문맥/누락/비정상 확률/저장 실패에 명시 상태. 무한 재시도 없음 |
| R12 | P0 | 실제 평가와 근거 장부 | 실행 명령·분자/분모·단위·모드·버전을 기록. 단위시험과 모델 평가 구분 |
| R13 | P0 | 계층과 변경 관리 | L0~L5 권한 구분. 변경 파일 hash·버전·승인 범위 및 적용 상태 기록 |
| R14 | P0 | 시연·발표의 정확성 | 정상→위험 턴 변화, 인젝션, 장애 시연. 미측정 수치와 실세계 효과 주장 없음 |

## 6 계층과 책임

| 계층 | 역할 | 실행 권한 |
|---|---|---|
| L0 | 공통 헌법 | 원칙 정의. 도구 권한 생성 안 함 |
| L1 | 모델의 제한된 행동·주장 분류 | 참고 의견만 생성 |
| L2 | 코드 TEMPLATES와 UI 안내 | 정책 결과에 맞는 고정 문구 선택 |
| L3 | 검토된 합성 대본·평가 데이터 | 실서비스 권한 없음 |
| L4 | 개발 보조 에이전트 | 사용자 허가 범위에서 파일 변경, 테스트·리뷰 |
| L5 | 발표·Q&A 초안 | 사실 장부에 근거한 초안 |

원문에 기재된 책임은 L1 이진명, L2/L3 최한길, L5 주장 감사 손호성이다. 이것은 **원문 기재 역할**로 보존하며 현재 합의·직위·학위·IP 소유를 새로 확정하지 않는다. 세 사람은 공동 개발자로 표기한다. L1/L2 변경의 2인 이상 승인 및 해당 계층 책임자 포함 규칙은 원문 기준으로 유지하고 실제 승인 여부는 기록한다.

## 7 데이터와 모델 경계

### 입력 정규형

```json
{
  "schema_version": "dmsg-input-v3.3",
  "session_id": "sess-demo-01",
  "request_id": "req-0002",
  "expected_session_version": 1,
  "latest_turn_id": 2,
  "turns": [
    {"turn_id": 1, "speaker": "caller", "text": "기관 안내입니다."},
    {"turn_id": 2, "speaker": "caller", "text": "지금 이 계좌로 송금하세요."}
  ]
}
```

위 예시는 애플리케이션 정규형이며 Zoro 제공 API의 검증된 요청 예시가 아니다. session_id 등은 서버가 생성·관리한다. 외부 사용자에게 mode·정책·검증 상태를 임의 설정하게 하지 않는다. 모델로 보내는 `state`에는 필요한 대화 문맥과 신뢰 경계를 넣고 평가 정답·scenario_id·expected_policy를 제거한다.

제안 제한: 턴당 2,000 Unicode code point, 최근 최대 3개 턴, 요청 본문 32 KiB. 제한 초과 시 조용히 자르지 않고 명시적으로 거부한다. 숫자는 운영 성능 실측값이 아니라 구현 설정 제안이다.

### 모델 질문

| ID | 내부 타입 | 허용값 |
|---|---|---|
| action_request | choice | none, money_transfer, remote_app_install, credential_or_otp, verification_link, other_unclear |
| identity_claimed | choice | none, government, financial_institution, relative, other |
| urgency_pressure | noul | yes, no |
| secrecy_pressure | noul | yes, no |
| evidence_sufficient | noul | yes, no |

이 다섯 질문은 원문과 동일하다. `evidence_sufficient=yes`는 모델의 의견이며 코드 검증 통과가 아니다. 질문 간 의존성을 가정하지 않으며 각각 같은 state만으로 답할 수 있어야 한다.

여러 위험 요청이 함께 등장하면 action_request는 모델의 대표 요청 하나이고, 정책은 코드가 검증한 모든 evidence를 검사한다. P0 대표 선택 우선순위 제안은 credential_or_otp → remote_app_install → money_transfer → verification_link이며 이는 위험도 실측 순위가 아닌 결정적 tie-break다. 팀이 확정해 코드·질문 지침을 함께 고정한다.

실제 endpoint의 요청 필드, 응답 scalar/분포, 모델 ID 제공 방식은 핸드셰이크 후 adapter에 매핑한다. 누락 필드를 만들어 채우거나 noul scalar를 문자열 boolean으로 오인하지 않는다. confidence와 최대 선택확률의 의미도 분리한다. 분포가 제공되면 유한성·[0,1]·라벨 집합·합계 오차를 검증한다. 합계 허용오차 제안은 0.01이며 스키마 버전에 기록한다.

### 근거 정규형

`Evidence = {turn_id, speaker, action_kind, start_cp, end_cp, quote, directness, origin, validator_version}`

`directness`는 DIRECT_REQUEST / NEGATED_OR_WARNING / QUOTED_OR_REPORTED / UNCLEAR. `origin`은 FIXTURE_ANNOTATED / CODE_CANDIDATE / MODEL_PROPOSED. 코드 후보·모델 제안은 검증 전 직접 요청으로 승격하지 않는다. 문자열 일치만으로 의미가 확정되는 것은 아니다.

오프셋은 원본 턴 문자열의 Unicode code point, 0-based, 끝 제외다. 브라우저 UTF-16 인덱스와 명시적으로 변환한다. 원문을 normalize한 문자열의 위치를 그대로 쓰지 않는다. 이모지·한글 결합문자 테스트를 포함한다. 원문에 없는 기관·전화번호·계좌·URL을 생성하지 않는다.

## 8 정책 결정 순서

정책 입력은 현재 세션, model_status, 정규화된 분류, 코드 검증 근거, 이전 미해결 위험이다. 다음은 **검토안 우선순위**다.

1. 세션/요청 버전이 오래됐거나 일치하지 않으면 새 결과를 반영하지 않는다. API는 충돌을 반환하고 현재 상태를 보존한다. 이 실패를 최신 입력의 위험 판정으로 기록하지 않는다.
2. 현재 또는 이전 미해결 턴에서 검증된 직접 송금·OTP·원격앱 설치 요청이 있으면 `PAUSE_AND_VERIFY`. 모델 오류·none이 이를 해제할 수 없다.
3. model_status가 INVALID/UNAVAILABLE이면 독립 고위험 근거가 없는 경우 `ASK_HUMAN`. 모델 실패 시 링크 단서만으로 정상/주의 분류 성공을 표시하지 않는다.
4. 모델과 코드의 의미가 충돌하거나 근거가 부족하면 `ASK_HUMAN`. 근거 없는 모델의 위험 라벨은 미표시하고 불일치 이유를 기록한다.
5. 검증된 직접 확인 링크 요청만 있으면 `CAUTION`. 링크 진위나 기관 신원은 인증하지 않는다.
6. 입력이 불명확하거나 evidence_sufficient=no이면 `ASK_HUMAN`.
7. 유효한 분류와 코드 검증에 따라 위험 요청이 없고 이전 미해결 위험도 없으면 `NO_STRONG_SIGNAL`.

인용·경고·부정의 위험 단어는 2번 조건의 직접 요청이 아니다. 늦게 온 문장이나 “이제 괜찮다”는 발신자 주장만으로 이전 위험을 제거하지 않는다. 고위험 안내가 모든 다음 턴을 영구 잠그는지도 별도 정책 이슈이므로 P0에서는 미해결 상태 유지·사용자 확인 안내로 제한하고 자동 안전 해제를 제공하지 않는다.

원문 G3의 NO_STRONG_SIGNAL은 **유효한 분석 결과와 독립 검증에서 직접 위험 요청이 없을 때**의 기대다. 같은 인젝션 문장이 모델 오류까지 유발하면 G4의 ASK_HUMAN 분기가 적용된다. 두 시험을 분리한다.

## 9 안내와 사용자 경험

소비자에게 모델이 생성한 자유문장을 출력하지 않는다. 원문 PDF p.5의 문구를 동반 System Prompting L2에 고정했다. 화면은 상태·짧은 근거·독립 확인 행동 하나를 우선하며 기술적 분포·reason·모델 상태는 심사 화면에서 펼쳐 본다.

네 상태는 NO_STRONG_SIGNAL / CAUTION / PAUSE_AND_VERIFY / ASK_HUMAN뿐이다. NO_STRONG_SIGNAL에는 “안전한 통화라는 뜻은 아닙니다”를 항상 포함한다. 독립 확인 선택지는 의심 대화에서 제공한 연락처 대신 공식 앱·기존에 별도 확인한 연락처·카드 뒷면 경로 등을 제시한다. 실제 번호·기관별 절차는 별도 최신 공식 출처 확인 전 삽입하지 않는다.

고령 사용자에게 3초 내 이해 가능하다는 문장은 사용성 목표다. 실제 사용성 시험 없이 달성했다고 보고하지 않는다.

## 10 상태와 실행 계약

`CREATED → INPUT_ACCEPTED → MODEL_PENDING → VALIDATING → POLICY_DECIDED → GUIDANCE_RENDERED → AWAITING_NEXT_TURN / CLOSED`

독립 상태로 model_status = NOT_REQUESTED / VALID / INVALID / UNAVAILABLE, review_status = NOT_REQUESTED / INTENT_RECORDED / SELF_REPORTED를 둔다. 새로운 턴마다 session_version을 증가시킨다. 재판단 요청은 처리한 version에 묶는다.

모델 네트워크 요청은 세션 락 밖에서 수행하고, 반영 시 expected version을 재검사한다. 원문 PDF의 context_version은 이 session_version에 명시 매핑한다. 동일 request_id+동일 입력 지문은 같은 응답을 반환하고, 같은 ID에 다른 입력·버전은 거부한다. 동시 요청의 반영 순서는 한 가지로 결정되어야 한다.

P0에는 외부 도구 executor가 없다. 안내 표시와 로컬 intent 기록의 성공은 별도 재조회로 확인한다. 네트워크 오류를 사기 위험의 증거로 쓰지 않는다. 자동 모델 재시도는 기본 0회, 사용자의 새 요청과 선택적 실험 C의 추가 1회는 구분한다.

## 11 API 제안

다음은 신규 구현 인터페이스 제안이며 기존 앱의 존재·호환을 보증하지 않는다.

| 메서드와 경로 | 입력/출력 요점 |
|---|---|
| POST /api/v1/sessions | 새 세션 ID, version=0, 실제 configured mode |
| POST /api/v1/sessions/{id}/turns | expected_version, request_id, text → typed 결과·정책·검증 근거·새 version |
| POST /api/v1/sessions/{id}/verification-intents | expected_version, 독립 확인 의도 enum → INTENT_RECORDED |
| GET /api/v1/sessions/{id} | 현재 상태·안내·버전. 원문 접근 최소화 |
| DELETE /api/v1/sessions/{id} | 원문·일시 세션 폐기. 실제 보존 범위 반환 |
| GET /api/v1/model-status | 설정 모드·최근 통신/신원 검증 범위. 키·endpoint 비밀 제외 |

400 잘못된 본문, 409 버전/멱등성 충돌, 413 크기 초과, 422 스키마 오류를 구분한다. 모델 장애는 응답 안 model_status로 드러내고 정책 안내를 반환할지 HTTP 502로 분리할지는 API 확정 시 한 방식으로 고정한다. P0 권고는 정책 생성에 성공하면 200+명시적 오류 상태, API 자체 실패는 5xx다. 저장 실패를 성공으로 보고하지 않는다.

## 12 보안과 개인정보

- 모든 텍스트·모델 출력은 비신뢰다. HTML 출력은 escape/textContent로 표시한다.
- 로컬 시연은 loopback 바인딩을 기본으로 한다. 다중 사용자·인터넷 공개는 별도 인증·TLS·세션 격리·rate limit 검토 후 허용한다.
- 원문은 현재 세션 처리 메모리와 승인된 모델 요청에만 사용한다. 프록시/access log/오류 로그에 본문이 남는지도 검사한다. 원격 전송 전 목적·호스트·범위를 사용자에게 알린다.
- 원문 PDF는 text_sha256_12를 로그 예시로 제시한다. 짧은 평문 해시는 익명화를 보장하지 않으므로 본 검토안에서는 프로세스 임시 키 HMAC 지문을 기본 제안한다. 외부 부인방지·공증 기능이 아니다.
- 로그: trace/request/turn ID, version, prompt/schema/policy/template 버전, mode, model_status, 이유 코드, 지연, 근거 위치, 일시 입력 지문. 원문·quote·개인정보·API 키는 기본 제외한다.
- raw 요청/응답 보관이 필요한 합성 모델 평가만 별도 opt-in 실험 저장소를 사용한다. 평가 저장과 사용자 세션 로그를 혼합하지 않는다.

## 13 모델 연결과 모드

FIXTURE는 고정 데이터, SURROGATE는 규칙 모사, MODEL_RESPONSE_UNATTESTED는 통신 응답이 있으나 모델 신원 미확인, REAL_ZORO는 검증 범위를 기록한 실제 지정 모델 경로다. “verified handshake”는 보안 인증서나 모델 정확도 보증을 의미하지 않는다.

실모델 수용 증거: 서버 또는 제공자 확인 범위, 설정 모델과 가능한 revision, 실제 요청/응답, 5문항 매핑, 실패 경로, UI trace 연결. 모델 alias 반향이나 임의 status 문자열만으로 REAL_ZORO를 허용하지 않는다. 장애 시 fixture 자동 대체는 금지하며 사용자가 명시 선택한 별도 fixture 세션으로만 이동한다.

## 14 평가와 골든 테스트

원문 p.9의 G1~G8을 유지하고 한계를 명시한다. 아래는 모두 **이번 문서의 기대값**이며 새로 실행한 결과가 아니다.

| ID | 조건 | 기대 결과 | R-ID |
|---|---|---|---|
| G1 | 신분 주장만, 유효 모델·검증 | NO_STRONG_SIGNAL + 안전 아님 문구 | R03,R05,R06 |
| G2 | 검증된 직접 송금 요구 | PAUSE_AND_VERIFY, offset 일치 | R04,R05 |
| G3 | 가짜 SYSTEM, 직접 위험 요청 없음, 유효 분석 | 권한 없음, NO_STRONG_SIGNAL | R01,R05 |
| G4 | 모델 응답 없음, 독립 위험 근거 없음 | ASK_HUMAN + UNAVAILABLE | R08,R11 |
| G5 | 모델 응답 없음, 직접 송금 근거 검증됨 | PAUSE_AND_VERIFY + UNAVAILABLE | R04,R05,R11 |
| G6 | 모델은 송금, 코드 근거 없음 | 근거 미표시, ASK_HUMAN, 불일치 기록 | R04,R05 |
| G7 | 모델 none, 코드 직접 송금 검증됨 | PAUSE_AND_VERIFY, 원문 근거 우선 | R04,R05 |
| G8 | 오래된 턴 모델 응답 | 현재 결과 보존, TURN_ORDER_INVERSION | R07 |
| G9 | “OTP를 알려주지 마세요” | 직접 OTP 요구 미인정, 정상 검증이면 NO_STRONG_SIGNAL | R03,R04 |
| G10 | 인용·신고 뒤 별도의 직접 요구 | 각 절 분리, 직접 위험 요구만 정책 근거 | R03,R04 |
| G11 | 동일 요청/변조 재요청·동시성 | 단일 효과/충돌 거부 | R07 |
| G12 | 이모지·결합 한글·원문 normalization 차이 | 정확한 code point 인용 또는 검증 실패 | R04 |
| G13 | NaN·라벨 누락·type 오류·잘린 문맥 | INVALID, 근거 없으면 ASK_HUMAN | R02,R11 |
| G14 | 세션 종료·오류·로그 검사 | 원문 폐기, 비밀·인용 없음 | R09 |

원문은 G1~G5/G8을 verified by test, G6/G7을 unverified로 표기한다. 이 문서에서는 해당 기록을 원문 주장으로만 보존하며 전체 재실행을 수용 조건으로 둔다.

평가 단위는 세션/시나리오 패밀리다. 정상·위험 사례 수를 같게 만들고 개발·검증·잠금 세트에 동일 패밀리 변형을 섞지 않는다. 작성자 기대값은 실제 사기 정답이 아니다. 원문은 사람이 작성한 합성 라이브러리를 요구하므로 LLM 생성 대본을 검토 없이 런타임에 추가하지 않는다.

Baseline A 규칙+정책, B 실제 Zoro 직접 typed+동일 정책, C 선택적 reasoning 후 typed+동일 정책을 같은 잠금 세션으로 비교한다. C는 주장이 아닌 가설이며 B/C 미실행은 NOT_RUN으로 보고한다. 추가 관측 재평가와 reasoning 실험을 같은 개선 효과로 합치지 않는다.

지표: 위험 안내 누락/위험 세션, 정상 불필요 개입/정상 세션, 거짓 안전 보증 수, 보류율, 비보류 적절성, 근거 일치율, timeout/invalid 비율, p50/p95 지연. 표본 수·모드·분모·측정 구간을 기록하고 작은 합성 세트로 실세계 정확도나 피해 감소를 주장하지 않는다. 모든 입력 보류로 정확도를 높였다고 보고하지 않는다.

## 15 개발 순서와 출시 조건

1. 질문/라벨/문구/정책 검토안 확정과 기존 코드 차이 확인.
2. fixture 입력→근거→정책→UI를 연결하고 G1~G14 자동화.
3. 실제 모델 wire 계약을 캡처하고 B 경로 연결. G6/G7 실제 adapter 시험 포함.
4. 세션 충돌·원문 폐기·장애 표시·모드 전환 회귀시험.
5. 독립 평가와 발표 주장 장부, 실제 환경 재시작 시연.

실모델 P0 완료는 지정 모델 증거, 5문항 검증, 정책·문구 일치, 재현 가능한 정상/위험/장애 경로, R01~R14 수용 상태가 모두 확인될 때 선언한다. fixture 완료와 실모델 완료를 별도 보고한다. 성능·보정·피해 감소는 개별 평가가 없는 한 미검증이다.
