## 0. 한 쪽 요약

1. **룰북(`rulebook/`)의 문제는 "판단이 틀린다"보다 "틀린 룰을 막지 못한다"에 가깝다.** 조치 권한 경계(제안만, 실행 없음)는 잘 되어 있다. 그러나 룰을 불러올 때 충돌·사각지대·위험 조치 무력화 검사가 없고, 실제 Zoro 응답을 읽는 기준이 Arena와 달라 실시간 경로에서 전부 보류로 빠질 수 있다.
2. **룰북은 Arena 데모 판단에 연결되어 있지 않다.** `[확인]` `arena/`, `integration/` 어디에서도 `rulebook`을 import하지 않는다. 실제 데모 판단은 `integration/v51_policy.py`(semantic policy `v54-semantic/2`)가 한다. 따라서 "룰북으로 업종을 갈아끼운다"는 발표 주장은 현재 코드상 별도 CLI 시연에 한정된다.
3. **실제 제품 판단(Zoro + v51 정책)의 핵심 약점은 세 가지다.**
   - 한국어 금액 표현을 정책이 못 읽는다. `[확인]` "2천만 원 보내" → 금액·송금 문맥 미감지.
   - 모든 판단에 같은 0.70 기준을 쓰므로, 놓치면 큰 손해인 경우와 과잉 보류를 따로 조정할 수 없다.
   - 평가셋이 너무 작고 AI가 작성한 라벨이다. `[문서]` 잠금 AI24의 필수중단 누락 2/7의 95% 신뢰구간은 8.2%~64.1%다.
4. 해결은 **판단 결과를 바꾸지 않는 수정(버그·계약·검사·기록)**을 먼저 하고, **판단 결과가 바뀌는 수정(기준값·우선순위·어휘)**은 새 잠금 평가셋을 만든 뒤 별도 PR로 한다. 이 순서는 AGENTS.md 규칙("새 잠금셋 없이 판단 튜닝 금지")과도 일치한다.

## 3. 룰북 결함별 해결 대안 비교

각 항목에서 **권장안**을 먼저 쓰고, 나머지 대안과 버리는 이유를 적는다.

### RB-1 응답 계약 불일치

| 대안 | 내용 | 장점 | 단점 | 판단 |
|---|---|---|---|---|
| A | `decide()` 앞에서 기존 `typed_contract.normalize_response`를 거친다 (룰북 질문 spec → `{type, options}` 변환) | 계약이 하나로 통일, Arena와 같은 수용 기준 | 룰북 고유의 엄격함(부가 필드 거부)을 잃음 | **권장** |
| B | 룰북 전용 어댑터를 따로 만든다 | 룰북 엄격성 유지 | 두 계약이 계속 따로 진화 → 같은 문제 재발 | 비권장 |
| C | 룰북 검사만 느슨하게 고친다 | 변경량 최소 | 형식 결정 근거가 없음 | 비권장 |

필수 선행: 실제 Zoro 응답 1건 이상을 캡처해 형식을 확정한다(현재 `NOT_RUN`). 캡처 전에는 "두 형식 모두 수용 + 어떤 형식이었는지 기록"이 안전하다.

### RB-2 무관 질문 확신도

| 대안 | 내용 | 판단 |
|---|---|---|
| A | 각 질문의 답을 확신도와 함께 먼저 계산하되, **기준 미달 질문은 "미정"으로 두고**, 미정 질문을 참조하지 않는 규칙만 성립 가능하게 한다. 성립한 규칙이 미정 질문을 참조하면 보류 | **권장** (정확히 필요한 질문만 검사) |
| B | 규칙마다 `required_questions`를 명시 | 명시적이나 `when`과 중복 정보 → 불일치 위험 |
| C | 현행 유지(전 질문 검사) | 보류 과다. 정상 문의가 사람 검토로 쌓임 |

주의 `[추론]`: A는 버그 수정이지만 **결과가 달라지는 수정**이다(지금 보류되던 일부가 NO_ACTION 등으로 바뀜). 프리셋 기준으로 "보류였던 사례 → 무엇이 되는가"를 표로 남기고 PR에 첨부한다.

### RB-3 충돌 해소 원칙

결정표 표준인 OMG DMN의 hit policy(UNIQUE / PRIORITY / FIRST 등)처럼, **충돌 시 어떤 원칙으로 고르는지를 룰북 파일에 명시**하게 하는 것이 핵심이다.

| 대안 | 내용 | 판단 |
|---|---|---|
| A | 조치에 **안전 서열**(`HOLD_FOR_REVIEW > OPEN_VERIFICATION_TASK > OPEN_REVIEW_TASK > REQUEST_INFORMATION > NO_ACTION`)을 고정. 동시 성립 시 가장 보수적 조치 채택. priority는 같은 서열 안에서만 사용 | **권장** (오타 하나로 검토 단계가 사라지는 경로 차단) |
| B | `hit_policy` 필드 도입(`UNIQUE`: 동시 성립 자체를 로드 시 금지 / `SAFEST`: A) | A를 기본값으로 하고 B는 확장 옵션으로 |
| C | 현행 priority 유지 + 경고만 | 경고는 무시되기 쉬움 |

A는 판단 결과가 바뀔 수 있으므로 별도 PR. 단, 현재 두 프리셋에서는 동시 성립이 없어 **프리셋 결과는 변하지 않는다** `[추론: 프리셋 조건이 상호배타]` → 테스트로 확인할 것.

### 4.2 현재 수치의 불확실성 `[문서 수치 + 확인 계산]`

| 지표 | 값 | 95% Wilson 구간 | 해석 |
|---|---|---|---|
| 잠금 AI24 필수중단 누락 | 2/7 | 8.2% ~ 64.1% | 7건으로는 "개선됐다/아니다"를 말하기 어려움 |
| 잠금 AI24 정상 불필요 ASK | 5/12 | 19.3% ~ 68.0% | 동일 |
| 개발 최종 필수중단 누락 | 3/39 | 2.7% ~ 20.3% | 개발셋이라 낙관 편향 가능 |
| 개발 불필요 정상 ASK | 21/64 | 22.6% ~ 45.0% | 과잉 보류가 실질적 문제 |

## 7. 소크라테스식 점검

> *(창작 문장이며 실제 인용이 아님)*
> "규칙을 많이 가진 자가 아니라, 규칙이 틀렸을 때 그것을 아는 자가 지혜롭다."
> "확신의 숫자가 사실의 숫자는 아니다."
> "일곱 번 본 것으로 천 번을 말하지 마라."

**반복되는 근거 부족 전제:** "룰북과 질문을 갈아끼우면 어느 업종에서든 정확하게 작동한다."

**반례 질문:** 계좌변경 프리셋에서 Zoro가 "변경 요청 확률 14%"라고 답한 송금 메시지는 확인 업무를 만들까?

**답:** 만들지 않는다(RB-4 재현, NO_ACTION·사람 확인 불요). 그리고 실제 문장이 "2천만 원 보내"라면 제품 정책은 금액조차 읽지 못한다(ZP-1 재현). 갈아끼울 수 있다는 것과 갈아끼운 뒤에도 맞는다는 것은 다른 주장이며, 후자는 업종별 잠금 평가 없이는 성립하지 않는다.

**전제가 성립하는 조건:** (1) 질문 의미가 업종 간 동일하고, (2) 룰북이 로드 시 충돌·사각지대 검사를 통과하고, (3) 해당 업종의 독립 잠금셋에서 누락·과잉 지표가 구간 포함 보고될 때.

**반증 가능한 실험:** 새 업종 룰북마다 "필수 확인 누락률 상한(예: 95% 구간 상단 ≤ 15%)"을 사전에 적고, 잠금셋 1회 실행으로 통과/실패를 기록한다. 실패도 장부에 남긴다.

## 8. SNM·4D 요약

**시나리오 네트워크 (룰북·정책 공통):** 정상 요청 / 직접 위험 / 부정·경고 / 과거 보고·인용 / 정보 누락(주문번호 없음) / 금액 변형 표현 / 모델 응답 형식 변형 / 모델 시간초과 / 규칙 충돌 / 사각지대 / 이전 위험 유지 / 재시도 중복 / 계약 변경 중 요청. 이 중 이번 검토에서 **방어 실패가 재현된 것**: 금액 변형(ZP-1), 응답 형식 변형(RB-1), 규칙 충돌 우선순위 무력화(RB-3), 무관 질문 불확실(RB-2).

**4D:**
- 구조: 입력 → Zoro 선택 → 계약 정규화(**두 개 존재: RB-1**) → 정책/룰북 → 제안 → (미구현) 승인·실행 → (미구현) 결과 확인.
- 시간: 룰북 버전·SHA는 기록되나 응답 형식 버전은 기록되지 않음 → RB-1 수정 시 함께 기록.
- 관점: 정상 상대방(과잉 보류 비용), 사용자(놓침 비용), 운영자(검토 피로), 심사위원(측정 근거).
- 역검증: 보류 결과에서 원인 질문으로 역추적 불가(RB-6) → 수정 대상.

**NPU:** 이 계층은 서버 Python에서 실행된다. NPU 관련 주장 근거 없음.
